Computer System Organization

•

Caching
OPERATING SYSTEMS
• Important principle, performed at many levels in a computer (in hardware, 
operating system, software)
• Information in use copied from slower to faster storage temporarily
• Faster storage (cache) checked first to determine if information is there
• If it is, information used directly from the cache (fast)
• If not, data copied to cache and used there
• Cache smaller than storage being cached
• Cache management important design problem
• Cache size and replacement policy

I/O Structure

Round-Robin Scheduling
OPERATING SYSTEMS
• Round-robin (RR) scheduling algorithm is designed especially for timesharing 
systems. 
• It is similar to FCFS scheduling, but preemption is added to enable the 
system to switch between processes
• A small unit of time, called a time quantum or time slice, is defined. 
• A time quantum is generally from 10 to 100 milliseconds in length
• The ready queue is treated as a circular queue
• The CPU scheduler goes around the ready queue, allocating the CPU to each 
process for a time interval of up to 1 time quantum

Round-Robin Scheduling Performance
OPERATING SYSTEMS
•
If there are n processes in the ready queue and the time quantum is q, then each 
process gets 1/n of the CPU time in chunks of at most q time units. 
•
Each process must wait no longer than (n − 1) × q time units until its next time 
quantum. 
•
For example, with five processes and a time quantum of 20 milliseconds, each process 
will get up to 20 milliseconds every 100 milliseconds.
•
Performance of the RR algorithm depends heavily on the size of the time quantum
•
If the time quantum is extremely large, the RR policy is the same as the FCFS 
policy
•
If the time quantum is extremely small, the RR approach can result in a large 
number of context switches

--------------------------------------------------------------------------------
Slide 10: Need for an Operating System
--------------------------------------------------------------------------------
• Question: "If an OS is not developed, then how will application developers access the hardware?"
• Diagram Illustration:
  [Application Developer / Programs]
                  |
                  v (Direct hardware manipulation without OS?)
  [Hardware: Monitor, Keyboard, Mouse, Printer, Hard Disk]

• Explanation:
  Without an operating system, every programmer would need to write low-level code specific to every peripheral device (handling device registers, timing signals, interrupt lines, device controllers, etc.). Applications would conflict with each other when competing for resources like memory and disk storage. The OS abstracts hardware complexity and offers uniform interfaces.

--------------------------------------------------------------------------------
Slide 11: General Definition of Operating System
--------------------------------------------------------------------------------
• Definition:
  - An Operating System is a program that acts as an intermediary between a user of a computer and the computer hardware.
  - It provides a user-friendly environment in which a user may easily develop and execute programs.
  - Otherwise, intricate hardware knowledge would be mandatory for computer programming.
• Layered Hierarchy Diagram:
  +---------------------------------------------------+
  |                       User                        |
  +---------------------------------------------------+

  +---------------------------------------------------+

  +---------------------------------------------------+

  +---------------------------------------------------+

  +---------------------------------------------------+
  |                  Hardware                         |
  +---------------------------------------------------+

--------------------------------------------------------------------------------
Slide 12: Operating System Goals
--------------------------------------------------------------------------------
• Primary Goals:
  1. Execute user programs and make solving user problems easier.
  2. Make the computer system convenient to use.
  3. Use computer hardware in an efficient manner.
  4. Manage resources such as:
     - Memory (RAM allocation, deallocation, protection)
     - Processor(s) (CPU scheduling, execution dispatch)
     - I/O Devices (device drivers, controllers, buffering)

--------------------------------------------------------------------------------
Slide 13: Why Study Operating Systems?
--------------------------------------------------------------------------------
• Motivation:
  - Only a small percentage of computer practitioners will be involved in the creation or modification of an operating system.
  - However, almost all code runs on top of an operating system.
  - Knowledge of how operating systems work is crucial to proper, efficient, effective, and secure programming.
  - Understanding the fundamentals of operating systems allows developers to write optimized, high-performance software.

--------------------------------------------------------------------------------
Slide 14 & 15: Computer System Structure (Four Components - Abstract View)
--------------------------------------------------------------------------------
• Silberschatz Figure 1.1: Abstract view of the components of a computer system:
  +-------------------------------------------------------------------------+
  |    User 1            User 2            User 3      ...     User n       |
  +-------------------------------------------------------------------------+
         |                 |                 |                     |
  +-------------------------------------------------------------------------+
  |  Compiler          Assembler         Text Editor        Database System |

  |                 (CPU, Main Memory, I/O Devices)                         |
  +-------------------------------------------------------------------------+

• Detailed Breakdown of the 4 Components:
  1. Hardware: Provides basic computing resources (CPU, memory, I/O devices).
  2. Operating System: Controls and coordinates the use of hardware among various applications and users.
  3. Application Programs: Define the ways in which system resources are used to solve the computing problems of users (word processors, compilers, web browsers, database systems, video games).
  4. Users: People, machines, or other computers issuing requests.

--------------------------------------------------------------------------------
Slide 16 & 17: What Operating Systems Do (User View vs. System View)
--------------------------------------------------------------------------------
• User View:
  - Varies depending on the interface:
    * PC / Workstation: Users desire convenience, ease of use, and high performance; resource utilization is secondary.
    * Mainframe / Minicomputer / Servers: Must keep multiple concurrent users happy; maximize resource utilization so that CPU, memory, and I/O are used efficiently and no individual monopolizes shared resources.
    * Workstations connected to servers: Dedicated personal resources combined with shared network resources (file, compute, print servers). The OS balances individual usability with resource utilization.
    * Handheld devices (Mobile / Smart Devices): Resource-poor, optimized for usability, battery life, and touch interactions.
    * Embedded computers (Automobiles, IoT, Appliances): Minimal or no user interface; run continuously without human intervention to control physical equipment.

--------------------------------------------------------------------------------
Slide 18 & 19: System View & Defining the Operating System
--------------------------------------------------------------------------------
• System View:
  - OS as a Resource Allocator:
    * Manages all resources (CPU time, memory space, file storage, I/O devices).
    * Acts as a referee between conflicting requests from programs and users for efficient and fair resource use.
  - OS as a Control Program:
    * Controls execution of user programs to prevent errors and improper use of the computer.
    * Especially concerned with the operation and control of I/O devices.
• Defining the Operating System:
  - The fundamental goal of computer systems is to execute user programs and make solving user problems easier.
  - Common functions of controlling and allocating resources are consolidated into one piece of software: the Operating System.
  - Technical Definition: "The one program running at all times on the computer" is the kernel.
  - Everything else is categorized as:
    1. A system program (ships with the OS, e.g., shell, file managers, editors).
    2. An application program (developed by users/third-parties to solve domain-specific tasks).

--------------------------------------------------------------------------------
Slide 20 & 21: Computer-System Organization & Modern Architecture
--------------------------------------------------------------------------------
• Organization:
  - A computer system consists of one or more CPUs and multiple device controllers connected through a common system bus providing access to shared memory.
  - CPUs and device controllers execute concurrently, competing for memory cycles.
  - A memory controller synchronizes access to the shared memory to ensure data integrity.

• Silberschatz Figure 1.2: Modern Computer System Organization:

--------------------------------------------------------------------------------
Slide 22: Computer-System Operation
--------------------------------------------------------------------------------
• Principles of Operation:
  - I/O devices and the CPU execute concurrently.
  - Each device controller is in charge of a specific device type (e.g., disk controller, USB controller).
  - Each device controller maintains local buffer storage and a set of special-purpose registers (control, status, data).
  - Data transfer process:
    1. CPU moves data from/to main memory to/from device controller local buffers.
    2. Device I/O operates between the physical device and the controller's local buffer.
    3. The device controller informs the CPU that it has completed its operation by triggering an interrupt.

--------------------------------------------------------------------------------
Slide 23: System Bootstrapping (Boot Process)
--------------------------------------------------------------------------------
• Boot Sequence:
  1. Power on / Reset: CPU register program counter (PC) is initialized to point to firmware.
  2. Bootstrap Program:
     - The first program that executes when a computer system is powered on or rebooted.
     - Stored in Read-Only Memory (ROM) or Electrically Erasable Programmable Read-Only Memory (EEPROM).
     - Known by the general term firmware.
     - Initializes all aspects of the system: CPU registers, device controllers, memory contents.
     - Locates the operating system kernel and loads it into main memory.
  3. Kernel Initialization:
     - The kernel sets up system services, interrupt vectors, and starts the initial process.
  4. Init Process:
     - The first user/system process created after the OS is booted (traditionally `init` or `systemd`).
     - Waits for events (like user login, daemon requests) to occur.

--------------------------------------------------------------------------------
Slide 24 & 25: Interrupts and Interrupt Handling
--------------------------------------------------------------------------------
• Core Concepts:
  - An modern operating system is interrupt-driven. If there are no processes to execute, no I/O devices to service, and no user input, the OS will sit idly waiting for events.
  - Events are signaled by interrupts.

• Classification of Interrupts:
                    +-----------------------+
                    |    Interrupt Event    |
                    +-----------------------+
                                |
             +------------------+------------------+
             |                                     |
    [ Hardware Interrupt ]                [ Software Interrupt ]
             |                                     |
    +--------+--------+                            |
    |                 |                            |
[ Polling ]      [ Vectored ]            [ Trap / Exception ]
                                         - Error (division by zero, invalid memory)
                                         - System Call (user request for OS service)

• Interrupt Handling Lifecycle:
  1. Interrupt Generation:
     - Hardware: Interrupt Request (IRQ) line sent by a device controller to the CPU.
     - Software: Exception/Trap triggered by illegal instruction, or software interrupt instruction executed.
  2. Processor Response:
     - The processor halts the current thread of execution at the end of the current instruction cycle.
  3. State Preservation:
     - The processor automatically saves the current CPU state (program counter, processor status word, registers) onto the stack or kernel stack.
  4. Interrupt Dispatching:
     - Determines the interrupt type:
       * Vectored Interrupt System: Hardware delivers an offset into an Interrupt Vector (array of pointers to specific interrupt service routines / ISRs).
       * Polling: CPU queries each device controller in order of priority to determine who requested service.
  5. Handler Execution:
     - The corresponding Interrupt Service Routine (ISR) executes to handle the condition (e.g., reading characters from buffer).
  6. State Restoration:
     - The saved registers and program counter are restored.
     - The interrupted thread resumes execution exactly where it was halted.

  - Interrupt processing time varies; device transfer time also varies.

Slide 27 & 28: Storage Structure & Program Execution Model
--------------------------------------------------------------------------------
• Main Memory:
  - The only large storage media that the CPU can access directly via memory bus.
  - Random Access Memory (RAM), typically volatile (loses content upon power loss).
  - Implemented using semiconductor Dynamic RAM (DRAM).
  - Other memory types: ROM, EEPROM (used for firmware and non-volatile device storage, e.g. factory settings in smartphones).

• Von Neumann Model of Computing (Instruction Execution Cycle):
  - Architecture: CPU contains Control Unit, Arithmetic/Logic Unit (ALU), and Registers.
  - Cycle:
         +----------------------------------------------------+
         |                 Main Memory (RAM)                  |
         +----------------------------------------------------+
                  | Fetch Instruction            ^ Store Data
                  v                              |
         +----------------------------------------------------+
         |                      CPU                           |
         |  [ Control Unit ] ------> [ ALU / Registers ]      |
         |    (Decode)                   (Execute)            |
         +----------------------------------------------------+
  - Steps:
    1. Fetch: The processor fetches an instruction from memory using the Program Counter (PC).
    2. Decode: The Control Unit decodes what operation must be performed and loads required operands.
    3. Execute: The Arithmetic/Logic Unit (ALU) performs the operation, updating registers and condition flags.
    4. Store: Results are written back to registers or memory.
    5. Repeat: Steps repeat until program terminates or halts.

--------------------------------------------------------------------------------
Slide 29 & 30: Secondary Storage & Storage Hierarchy
--------------------------------------------------------------------------------
• Secondary Storage:
  - Extension of main memory providing large, nonvolatile storage capacity.
  - Hard Disk Drives (HDD):
    * Rigid metal or glass platters coated with magnetic recording material.
    * Disk surface is logically organized into tracks, subdivided into sectors.
    * Disk controller manages the physical and logical interactions.
  - Solid-State Drives (SSD):
    * Nonvolatile semiconductor memory (NAND flash).
    * Much faster access times, no moving parts, widely used in mobile, laptops, and data centers.

• Storage Hierarchy Principles:
  Storage systems are organized hierarchically based on three fundamental trade-offs:
  1. Speed (Access Time)
  2. Cost (Cost per bit)
  3. Volatility (Persistence of data across power cycles)

--------------------------------------------------------------------------------
Slide 31: Storage-Device Hierarchy Pyramid
--------------------------------------------------------------------------------
• Silberschatz Figure 1.6:

               /\
              /  \
             /    \             [ REGISTERS ]
            /------\
           /        \           [ CACHE ]
          /----------\                               PRIMARY / VOLATILE
         /            \         [ MAIN MEMORY ]       STORAGE
        /==============\ ==========================
       /                \
      /  NON-VOLATILE    \      [ NVRAM / SSD / FLASH ]
     /     MEMORY         \
    /----------------------\                          SECONDARY / NON-VOLATILE
   /                        \   [ HARD-DISK DRIVES ]   STORAGE
  /--------------------------\
 /        OPTICAL DISK        \
/------------------------------\                      TERTIARY STORAGE
/       MAGNETIC TAPES          \
----------------------------------

  Directional Properties:
  ▲ Upward: Higher cost per bit, faster access time, smaller capacity.
  ▼ Downward: Lower cost per bit, slower access time, larger capacity.
  - Volatile Storage (Registers, Cache, Main Memory): Loses data on power loss.
  - Nonvolatile Storage (NVRAM, Hard Disks, Optical Disks, Tapes): Retains contents without power.

--------------------------------------------------------------------------------
Slide 32: Caching
--------------------------------------------------------------------------------
• Caching Principle:
  - Information in use is copied temporarily from slower storage to faster storage.
  - Performed at multiple levels: hardware (L1/L2/L3 CPU caches), operating system (disk cache, page cache in RAM), and software (browser cache, application cache).
  - Workflow:
    1. Check faster storage (cache) first.
    2. If found (Cache Hit), data is read directly from fast cache.
    3. If not found (Cache Miss), data is fetched from slower storage, copied into cache, and delivered to requester.
  - Cache size is necessarily smaller than the backing store.
  - Cache Management & Replacement Policies (LRU, FIFO, etc.) are central design challenges.

--------------------------------------------------------------------------------
Slide 33, 34 & 35: I/O Structure and Execution Modes
--------------------------------------------------------------------------------
• I/O Overview:
  - A large portion of operating-system code is dedicated to managing I/O because system reliability and performance depend heavily on it.
  - General-purpose computer consists of CPUs and multiple device controllers connected via a common bus.
  - Device Driver:
    * Software module written for each device controller.
    * Provides a uniform interface between the controller hardware and the kernel.
  - Small Computer-Systems Interface (SCSI):
    * Controller architecture that supports daisy-chaining multiple devices.
  - Device Controller Components:
    * Local buffer storage.
    * Special-purpose registers (command, status, data-in, data-out).
    * Logic to move data between the peripheral device and the local buffer.

• Synchronous vs. Asynchronous I/O Modes:
  1. Synchronous I/O (Waiting for completion):
     - After I/O starts, control returns to the user program only upon I/O completion.
     - The CPU executes a wait instruction (or tight polling loop) idling until the next interrupt.
     - At most one I/O request is processed at a time; no concurrent I/O.
  2. Asynchronous I/O (Concurrent execution):
     - After I/O starts, control returns immediately to the user program without waiting for I/O completion.
     - A system call allows a user program to explicitly wait for I/O completion when needed.
     - Device-Status Table:
       * Kernel maintains a table containing an entry for each I/O device indicating device type, bus address, and current state (idle, busy, transferring).
       * If device is busy, additional requests are queued.
       * OS indexes into this table upon interrupt to locate the corresponding device handler.

--------------------------------------------------------------------------------
Slide 36: Direct Memory Access (DMA)
--------------------------------------------------------------------------------
• DMA Purpose and Architecture:
  - Standard interrupt-driven I/O produces an interrupt per byte (or word), which wastes significant CPU cycles for high-speed devices (like gigabit Ethernet or NVMe/SATA disks).
  - Direct Memory Access (DMA) solves this for high-speed I/O devices capable of transmitting information close to memory bus speeds.

• DMA Operation:
  1. Setup: CPU programs the DMA controller with source address, destination address, transfer direction, and transfer counter (number of bytes).
  2. Block Transfer: The device controller transfers entire blocks of data directly between its buffer storage and main memory without any CPU intervention.
  3. Completion: Only one interrupt is generated per block of data transferred, rather than one interrupt per byte.
  4. Concurrency: The CPU continues executing user instructions in parallel while data movement occurs across the bus.

Slide 4: Computer-System Architecture - Single & Special-Purpose Processors
--------------------------------------------------------------------------------
• Most systems traditionally use a single general-purpose processor (the main CPU).
• Most modern systems also contain special-purpose processors:
  - Device-specific microprocessors: embedded inside disk drives, keyboard controllers, graphics cards (GPUs).
  - Special-purpose processors run a limited instruction set and perform dedicated functions.
  - Low-level components built into hardware, monitored and managed by the OS.
• Example: Disk Controller Microprocessor:
  - Receives a high-level sequence of read/write requests from the main CPU.
  - Maintains and implements its own disk queue and disk arm scheduling algorithm.
  - Relieves the main CPU of the computational overhead of disk scheduling and track-level management.

--------------------------------------------------------------------------------
Slide 5: Multiprocessor Systems (Parallel / Tightly-Coupled Systems)
--------------------------------------------------------------------------------
• Multiprocessor systems have grown in prevalence and importance.
• Characteristics:
  - Contain two or more processors in close communication.
  - Share the computer bus, clock, memory, and peripheral devices.
• Key Advantages:
  1. Increased Throughput:
     - More processors execute more work in less time.
     - Note: Speedup ratio is not strictly N times for N processors due to overhead from synchronization, contention for shared resources, and inter-processor communication.
  2. Economy of Scale:
     - Multiprocessor systems cost less than equivalent multiple single-processor systems because they share peripherals, mass storage, and power supplies.
  3. Increased Reliability (Fault Tolerance / Graceful Degradation):
     - If functions can be distributed properly among several processors, the failure of one processor does not halt the entire system.
     - The system continues operating at reduced capacity (Graceful Degradation).
     - Systems designed for graceful degradation are called fault tolerant.

--------------------------------------------------------------------------------
Slide 6 & 7: Multiprocessor Types & Symmetric Multiprocessing (SMP) Architecture
--------------------------------------------------------------------------------
• Two Types of Multiprocessor Systems:
  1. Asymmetric Multiprocessing (AMP):
     - Boss-worker (Master-Slave) relationship.
     - A master processor controls the system, schedules processes, and allocates work to worker processors.
     - Worker processors execute predefined tasks or wait for instructions.
  2. Symmetric Multiprocessing (SMP):
     - All processors are peers; no master-slave relationship exists.
     - Each processor performs all tasks within the operating system (kernel and user code).
     - Each processor has its own private registers and local cache.
     - All processors share the same physical memory via a common system bus.

Slide 9: Blade Servers

Slide 10 & 11: Clustered Systems

Slide 12: Operating-System Structure - Multiprogramming
--------------------------------------------------------------------------------
• Need for Multiprogramming (Batch Systems):
  - A single user/job cannot keep both the CPU and I/O devices busy at all times.
  - Multiprogramming organizes jobs (code and data) such that the CPU always has a job to execute, maximizing CPU utilization.
• How Multiprogramming Works:
  1. A subset of all jobs in the system is kept simultaneously in main memory.
  2. The OS selects and runs one job via job scheduling.
  3. When that job must wait (for an I/O request, disk read, or user input), the OS context-switches the CPU to another ready job.
  4. The CPU never sits idle as long as at least one job is ready to run.

Slide 13: Operating-System Structure - Multitasking (Time-Sharing)
--------------------------------------------------------------------------------
• Definition:
  - Multitasking (Time-sharing) is a logical extension of multiprogramming.
  - The CPU switches between jobs so frequently that users can interact with each program while it runs, creating interactive computing.
• Requirements:
  - Response time should be rapid (< 1 second).
  - Each active user has at least one executing program in memory, called a **Process**.
  - CPU Scheduling: If several processes are ready to execute concurrently, the CPU scheduler picks the next process.
  - Virtual Memory & Swapping: If processes cannot entirely fit in physical RAM, swapping and virtual memory mechanisms move processes between memory and disk storage.

--------------------------------------------------------------------------------
Slide 14: Operating-System Operations - Interrupt-Driven Nature
--------------------------------------------------------------------------------
• Modern operating systems are interrupt-driven.
• Two fundamental classes of interrupts:
  1. Hardware Interrupt:
     - Triggered by hardware devices (timer, keyboard, network card, disk controller) asserting signals on the CPU's interrupt request line.
  2. Software Interrupt (Trap or Exception):
     - Generated by the CPU hardware while executing instructions.
     - Triggered by:
       * Software errors: division by zero, invalid memory address access (segmentation fault).
       * Explicit requests for OS services: executing a system call instruction (e.g., read, write, fork).
       * Other issues: infinite execution loops or malicious attempts to alter kernel data structures.

--------------------------------------------------------------------------------
Slide 15 & 16: Dual-Mode and Multi-Mode Operations
--------------------------------------------------------------------------------
• Need for Dual-Mode:
  - Protect the operating system from erroneous or malicious user programs, and protect user programs from one another.
• Hardware Support (The Mode Bit):
  - A dedicated bit in the CPU's processor status word (PSW) indicates current execution privilege:
    * **User Mode**  -> Mode Bit = 1
    * **Kernel Mode** (also Supervisor Mode, System Mode, Privileged Mode) -> Mode Bit = 0
• Privileged Instructions:
  - Certain critical CPU instructions can ONLY be executed in kernel mode (e.g., direct I/O manipulation, clearing interrupts, setting timer counters, modifying page tables).
  - If an attempt is made to execute a privileged instruction in user mode, the hardware treats it as illegal and triggers a trap (exception) to the OS.
• Multi-Mode Operation:
  - Modern CPUs support additional mode levels, such as Virtual Machine Manager (VMM) mode to support virtualization and guest operating systems securely.

• Silberschatz Figure 1.13: Transition from User to Kernel Mode:

      USER MODE (Mode bit = 1)                 KERNEL MODE (Mode bit = 0)
  +-------------------------------+         +-------------------------------+
  | User Process executing        |         |                               |
  |                               |         |                               |
  | Calls system call             |         |                               |
  | (e.g. read())                 |         |                               |
  |         |                     |         |                               |
  |         v                     |         |                               |
  |   [ TRAP / SYSCALL ] -------->|-------->| System call handled           |
  |   (Hardware sets bit = 0)     |         | Execute privileged routine    |
  |                               |         |         |                     |
  |                               |         |         v                     |
  |                               |<--------|<--- [ RETURN-FROM-TRAP ]      |
  | Resume user execution <-------+         |     (Hardware resets bit = 1) |
  +-------------------------------+         +-------------------------------+

• Transition Lifecycle:
  1. User program executes in user mode (bit = 1).
  2. Program needs OS service and executes a system call (trap).
  3. Hardware traps, saves CPU state, and switches mode bit to 0 (kernel mode).
  4. Kernel looks up the system call table, verifies parameters, and executes the privileged function.
  5. Upon completion, kernel executes a privileged return-from-trap instruction.
  6. Hardware restores state and sets the mode bit back to 1 (user mode).
  7. Control returns to the user process.

--------------------------------------------------------------------------------
Slide 17: Timer and CPU Protection
--------------------------------------------------------------------------------
• Purpose of Timer:
  - Prevent user programs from getting stuck in infinite loops or failing to yield control, thereby hogging the CPU indefinitely.
• Mechanism:
  1. A hardware timer is set to interrupt the CPU after a specified time interval:
     - Fixed period (e.g., 1/60th second) or variable period (e.g., 1 millisecond to 1 second).
  2. Variable timers are implemented using a fixed-rate clock and an internal counter.
  3. The operating system loads the initial counter value using a **privileged instruction** before dispatching a user process.
  4. Every clock tick, the counter decrements by 1.
  5. When the counter reaches zero, a hardware timer interrupt occurs.
  6. The interrupt transfers control back to the operating system's scheduler, enabling the OS to preempt the current process and assign the CPU to another task.

Slide 5, 6 & 7: OS Services Helpful to the User
--------------------------------------------------------------------------------
1. User Interface (UI):
   - Command-Line Interface (CLI): Shells / command interpreters that read and execute text commands typed by users.
   - Graphical User Interface (GUI): Window-based system with mouse/pointer interactions, menus, and icons.
   - Batch Interface: Commands and directives entered via batch script files without real-time human interaction.
2. Program Execution:
   - System must load executable programs into memory, schedule CPU time, allocate resources, and handle normal/abnormal termination.
3. I/O Operations:
   - Running programs frequently require I/O (files, network connections, display, keyboard). Users cannot access hardware directly; the OS provides safe, abstracted I/O mechanisms.
4. File-System Manipulation:
   - Creation, deletion, reading, writing, searching files and directories; querying metadata and managing read/write/execute permissions.
5. Communications:
   - Processes exchange information on the same computer (Inter-Process Communication / IPC) or across networked systems:
     * Shared Memory: Common memory region accessed directly by communicating processes.
     * Message Passing: Packets of information moved between processes by the operating system kernel.
6. Error Detection:
   - OS must continually detect and handle errors occurring in CPU/memory hardware, I/O devices (paper out, network disconnect), or user programs (arithmetic overflow, illegal memory access).
   - Provides debugging facilities, core dumps, and consistent logging.

--------------------------------------------------------------------------------
Slide 8 & 9: OS Services for System Efficiency & Protection
--------------------------------------------------------------------------------
1. Resource Allocation:
   - Efficient, fair distribution of resources (CPU cycles, main memory frames, disk storage, I/O devices) among multiple concurrent users and processes.
2. Accounting:
   - Keeps precise track of which users/processes consume how much and what kinds of system resources (for billing, capacity planning, and performance optimization).
3. Protection and Security:
   - Protection: Ensuring all access to system resources (memory, CPU, files) is controlled, authenticated, and isolated so concurrent processes do not interfere with each other.
   - Security: Defending the entire system against external intrusions, unauthorized users, malware, and network attacks.

Slide 10: System Calls & Example Sequence (File Copy)
--------------------------------------------------------------------------------
• System Calls:
  - The programmatic interface to services provided by the operating system kernel.
  - Written in C/C++ or assembly language; exposed via Application Programming Interfaces (APIs).

• Silberschatz Figure 2.2: Example System Call Sequence for Copying Source File to Destination:
  1. Acquire input file name:
     - Issue write() system call to display prompt on screen.
     - Issue read() system call to accept input from keyboard.
  2. Acquire output file name:
     - Issue write() system call to display prompt on screen.
     - Issue read() system call to accept input from keyboard.
  3. Open input file:
     - Issue open() system call; if file does not exist, issue system call to abort and print error.
  4. Create destination file:
     - Issue create() or open(O_CREAT) system call; if file already exists, abort or truncate.
  5. Copy Loop:
     - Issue read() system call from input file buffer.
     - Issue write() system call to destination file buffer.
     - Repeat until read returns 0 (End-Of-File / EOF) or error occurs.
  6. Clean up:
     - Issue close() system call on input file.
     - Issue close() system call on destination file.
  7. Output status message:
     - Issue write() system call to display completion message.
  8. Termination:
     - Issue exit() system call for normal termination.

Slide 13, 14 & 15: Process Concept & Process Memory Layout
--------------------------------------------------------------------------------
• Definition:
  - A **Program** is a passive entity (an executable file containing machine instructions stored on disk).
  - A **Process** is an active entity (a program in execution with an execution context, program counter, registers, and memory space).
  - A program becomes a process when its executable file is loaded into main memory.
  - Multiple processes can execute instances of the same program (e.g. multiple users opening the text editor).

• Silberschatz Figure 3.1 & C Memory Layout:

  High Memory (0xFFFFFFFF in 32-bit)
  +---------------------------------------------------+
  | Command-line arguments & Environment variables    |
  | (argc, argv, envp)                                |
  +---------------------------------------------------+
  | STACK                                             |
  | (grows downwards: function frames, local vars,    |
  |  parameters, return addresses)                    |
  |         |                                         |

  |                                                   |

  +---------------------------------------------------+

  +---------------------------------------------------+

• Concrete C Program Mapping Example:
  #include <stdio.h>
  #include <stdlib.h>

  int x;              // -> Uninitialized Data (BSS)
  int y = 15;         // -> Initialized Data

      int *values;    // -> Stack (local pointer)
      int i;          // -> Stack (local variable)

      values = (int *)malloc(sizeof(int) * 5); // -> Heap (allocated block)
      for (i = 0; i < 5; i++) {
          values[i] = i;                       // -> Text (code execution)
      }

• Linux Kernel Representation (`struct task_struct`):
  - Contains `pid_t pid`, `volatile long state`, `struct mm_struct *mm` (memory mapping), `struct files_struct *files` (open file descriptor table), `struct task_struct *parent`, `struct list_head children`.

--------------------------------------------------------------------------------
Slide 19 & 20: Process Scheduling & Types of Processes
--------------------------------------------------------------------------------
• Scheduling Objective:
  - Maximize CPU utilization and enable responsive time-sharing.
  - The process scheduler selects among available processes for CPU dispatch.
• Scheduling Queues:
  - Job Queue: Set of all processes in the system.
  - Ready Queue: Set of all processes residing in main memory that are ready and waiting to execute.
  - Device / Waiting Queues: Set of processes waiting for a specific I/O device or event.
• Process Characteristics:
  - I/O-Bound Process: Spends more time doing I/O than computations; characterized by many short CPU bursts.
  - CPU-Bound Process: Spends more time performing computations; characterized by few, very long CPU bursts.
  - The scheduler strives to maintain a balanced process mix of I/O-bound and CPU-bound jobs.

--------------------------------------------------------------------------------
Slide 21: Queueing-Diagram Representation of Process Scheduling
--------------------------------------------------------------------------------

                                |

                             [ CPU ]
                                |

Slide 22: Context Switch from Process to Process
--------------------------------------------------------------------------------
• Silberschatz Figure 3.5: Context Switch Sequence between Process P0 and Process P1:

  Process P0                  Operating System                 Process P1
  -------------------------------------------------------------------------
  Executing
      |
  [ Interrupt / Syscall ]
      |
      +---------------------> Save state into PCB_0
                              (CPU idle for user)

                                                                  |

      |

• Context Switch Details:
  - Saving the state of the active process into its PCB and restoring the state of the scheduled process from its PCB.
  - Context-switch time is pure system overhead; the CPU performs no productive user work while switching.
  - Dependent on hardware architecture, register sets, and memory management complexity (e.g., flushing TLB).

--------------------------------------------------------------------------------
Slide 23 & 24: Schedulers & Medium-Term Scheduler (Swapping)
--------------------------------------------------------------------------------
• Scheduler Types:
  1. Short-Term Scheduler (CPU Scheduler):
     - Selects which ready process in memory executes next on the CPU.
     - Invoked very frequently (milliseconds) -> must be extremely fast.
  2. Long-Term Scheduler (Job Scheduler):
     - Selects which processes from mass storage are admitted into memory into the ready queue.
     - Invoked infrequently (seconds, minutes) -> controls the **Degree of Multiprogramming**.
  3. Medium-Term Scheduler (Swapper):
     - Added when the degree of multiprogramming needs to be reduced due to memory overcommitment.
     - Temporarily removes processes from RAM and stores them on disk (Swap Out).
     - Later brings the process back into RAM to continue execution (Swap In).

• Silberschatz Figure 3.6: Swapping Architecture:
  +---------------+        +-------+
  |  READY QUEUE  | -----> |  CPU  |
  +-------^-------+        +---+---+
          |                    |
          | (Swap In)          | (Swap Out)
          |                    v
  +-------+--------------------+---+
  |    Partially Executed Processes|
  |       (Swapped-out to Disk)    |
  +--------------------------------+

Slide 25: Context Switch Overhead
--------------------------------------------------------------------------------
• When switching processes, the OS must:
  - Save general-purpose registers, program counter, stack pointer, floating-point registers.
  - Flush or invalidate the Translation Lookaside Buffer (TLB).
  - Switch memory address spaces (change page table base registers).
• Overhead Factors:
  - Modern CPUs provide multiple hardware register sets to speed up switching.
  - Complexity of the operating system and PCB size directly determines switch latency.

• Resource Sharing Options:

  2. Children share a subset of the parent's resources (prevents resource overload).
  3. Parent and child share no resources (isolated execution).
• Execution Options:
  1. Parent and children execute concurrently.
  2. Parent waits until some or all of its children terminate.

--------------------------------------------------------------------------------
Slide 6 & 7: Process Creation using fork() and exec()
--------------------------------------------------------------------------------
• Mechanics of fork() and exec():
  - `fork()`: Creates a new process. The child process is an exact copy of the parent's address space (data space, heap, stack, file descriptors).
  - `exec()`: Overwrites the process's memory space (text, data, heap, stack) with a completely new program from disk and begins execution at `main()`.

• Silberschatz Figure 3.8: Process Creation Sequence:

       PARENT PROCESS                              CHILD PROCESS
  +-----------------------+
  | Executes code         |
  | Calls fork() ---------+-------------------> +-------------------------+
  |                       |                     | Child process created   |
  | Checks pid:           |                     | Checks pid:             |
  |   pid > 0 (Child PID) |                     |   pid == 0              |
  | Calls wait()          |                     | Calls exec()            |
  |         |             |                     | (Overlays memory)       |
  |         v (Blocks)    |                     | Executes new program    |
  |         .             |                     | Calls exit()            |
  |         .             |<--------------------+                         |
  | Wakes up & resumes    |      Child terminates
  | Completes execution   |
  +-----------------------+

• Complete C Code Example (Slide 7):
  #include <stdio.h>
  #include <unistd.h>
  #include <sys/types.h>
  #include <sys/wait.h>

  int main() {
      pid_t pid;

      /* Fork a child process */
      pid = fork();

      if (pid < 0) {
          /* Error occurred */
          fprintf(stderr, "Fork Failed\n");
          return 1;
      }
      else if (pid == 0) {
          /* Child process: execute /bin/ls */
          execlp("/bin/ls", "ls", NULL);
      }
      else {
          /* Parent process: wait for child to complete */
          wait(NULL);
          printf("Child Complete\n");
      }

      return 0;
  }

--------------------------------------------------------------------------------
Slide 8 & 9: Process Termination (Normal, Abnormal, Cascading, Zombies & Orphans)
--------------------------------------------------------------------------------
• Process Termination Mechanisms:
  - Normal: Process executes its final statement or explicitly calls `exit(status)`.
    * Kernel deallocates physical memory, file locks, open file descriptors.
    * Returns exit status data from child to parent (reaped via `wait()`).
  - Abnormal: Parent or OS terminates child using `abort()` or signals:
    * Child exceeds allocated resource limits (CPU time, memory quotas).
    * Task assigned to child is no longer required.
    * Parent exits in an operating system that prohibits orphan processes.

• Cascading Termination:
  - If a process terminates (normally or abnormally), some operating systems mandate that all its descendant children, grandchildren, etc. must also be terminated. Initiated by the kernel.

• Zombie vs. Orphan Processes:
  1. **Zombie Process**:
     - A process that has terminated via `exit()`, but whose parent has NOT yet invoked `wait()`.
     - Its entry in the process table remains to preserve its PID and exit status for the parent.
     - When parent calls `wait()`, the zombie is reaped and removed from the process table.
  2. **Orphan Process**:
     - A child process whose parent process terminated without waiting for it.
     - The operating system resolves this by re-parenting the orphan to `init` (or `systemd`, PID 1).
     - `init` / `systemd` periodically invokes `wait()` to collect exit statuses and reap orphaned children.

--------------------------------------------------------------------------------
Slide 10: System Calls for Process Management - Process Identifiers
--------------------------------------------------------------------------------
• Properties of PIDs:
  - Every process is assigned a unique, non-negative integer identifier: Process ID (PID).
  - Used by system calls to target specific processes (signals, priority modification).
  - PIDs are finite and reused after processes terminate.
  - Modern Unix/Linux systems use delay-reuse algorithms to prevent race conditions where a newly created process accidentally receives the PID of a recently dead process.

--------------------------------------------------------------------------------
Slide 11: The fork() System Call
--------------------------------------------------------------------------------
• Prototype:
  #include <unistd.h>
  pid_t fork(void);

• Return Value Characteristics:
  - In Child: Returns 0.
  - In Parent: Returns the PID of the newly created child process (> 0).
  - On Failure: Returns -1 (e.g. system process limit reached).
• Address Space Semantics:
  - The child is an exact copy of the parent's data segment, heap, and stack.
  - In modern OSs, Copy-on-Write (COW) is used: parent and child share physical pages read-only until one attempts to write, whereupon the page is duplicated.

--------------------------------------------------------------------------------
Slide 12: The exit() System Call & Termination Types
--------------------------------------------------------------------------------
• Five Normal Termination Paths:
  1. Executing `return` from `main()`.
  2. Calling the standard C library `exit()` function (flushes I/O buffers, calls registered `atexit` handlers).
  3. Calling the direct kernel system call `_exit()` or `_Exit()`.
  4. Executing a return from the initial start routine of the last thread in the process.
  5. Calling `pthread_exit()` from the last thread in the process.

• Three Abnormal Termination Paths:
  1. Calling `abort()` (generates `SIGABRT` signal).
  2. Receiving certain terminating signals from the OS or other processes (e.g., `SIGKILL`, `SIGSEGV`, `SIGFPE`).
  3. The last thread responds to a thread cancellation request.

--------------------------------------------------------------------------------
Slide 13: The wait() and waitpid() System Calls
--------------------------------------------------------------------------------
• Prototypes:
  #include <sys/wait.h>
  pid_t wait(int *statloc);
  pid_t waitpid(pid_t pid, int *statloc, int options);

• Behavior of wait():
  - Blocks the caller if any child is actively running until one child terminates.
  - Returns immediately with termination status if a child has already terminated (zombie).
  - Returns -1 with `errno` set to `ECHILD` if the process has no children.
  - Receives `SIGCHLD` signal asynchronously upon child state change.
• Behavior of waitpid():
  - `pid > 0`: Wait for specific child whose PID equals `pid`.
  - `pid == -1`: Wait for any child process (identical to `wait()`).
  - `pid == 0`: Wait for any child in the same process group.
  - `pid < -1`: Wait for any child whose process group ID equals `|pid|`.
  - Options (e.g., `WNOHANG`): Non-blocking mode; returns 0 if status not available.

--------------------------------------------------------------------------------
Slide 14: The waitid() System Call
--------------------------------------------------------------------------------
• Prototype:
  #include <sys/wait.h>
  int waitid(idtype_t idtype, id_t id, siginfo_t *infop, int options);

• Features:
  - Allows fine-grained specification of which child state change to wait for.
  - `idtype`: `P_PID` (specific PID), `P_PGID` (process group), `P_ALL` (all children).
  - Returns 0 on success, -1 on failure.

Slide 15: The exec() Family of Functions
--------------------------------------------------------------------------------
• Prototypes:
  #include <unistd.h>
  int execl(const char *pathname, const char *arg0, ... /*, (char *)0 */);
  int execv(const char *pathname, char *const argv[]);
  int execle(const char *pathname, const char *arg0, ... /*, (char *)0, char *const envp[] */);
  int execve(const char *pathname, char *const argv[], char *const envp[]);
  int execlp(const char *filename, const char *arg0, ... /*, (char *)0 */);
  int execvp(const char *filename, char *const argv[]);
  int fexecve(int fd, char *const argv[], char *const envp[]);

• Mnemonic Decoding:
  - `l` (List): Arguments are passed individually as variable arguments ending with `(char *)NULL`.
  - `v` (Vector): Arguments are passed as an array of pointers (`char *argv[]`).
  - `p` (Path): Takes a filename and searches through directories listed in the `PATH` environment variable.
  - `e` (Environment): Allows caller to pass custom environment variables via `char *const envp[]`.
  - `f` (File Descriptor): Executes file referenced by an open file descriptor.

Slide 17: Race Conditions
--------------------------------------------------------------------------------
• Definition:
  - Occurs when multiple processes access and manipulate shared resources, and the execution outcome depends on the unpredictable order in which CPU scheduling occurs.
• Post-fork() Race:
  - After `fork()`, whether parent or child runs first depends purely on the OS scheduler.
  - Never write code that presumes parent runs first or child runs first.
• Flawed Polling Loop:
  while (getppid() != 1) {
      sleep(1);
  }
  - Inefficiently attempts to detect parent termination by checking if re-parented to `init`. Wastes CPU cycles and induces latency.

--------------------------------------------------------------------------------
Slide 18: I/O Request Life Cycle (I/O-Bound Process)
--------------------------------------------------------------------------------
• Sequence of Events:
  1. Running: Process executes on the CPU until it issues an I/O system call (e.g. read/write).
  2. Blocked: OS transitions process to the Waiting / Blocked queue.
  3. Preemption: CPU is immediately reassigned to another ready process in the ready queue.
  4. Device Servicing: Device controller processes transfer asynchronously.
  5. Interrupt: Device signals completion via hardware interrupt to the CPU.
  6. Ready: OS interrupt handler moves process from Waiting queue back to Ready queue.
  7. Resume: Scheduler dispatches process back to CPU for brief computation before next I/O.

--------------------------------------------------------------------------------
Slide 4 & 5: CPU Scheduling - Basic Concepts
--------------------------------------------------------------------------------
• Motivation:
  - In a system with a single CPU core, only one process can execute at any instant.
  - All other processes must wait in the ready queue until the CPU is freed and rescheduled.
  - Objective of Multiprogramming: Have some process running at all times to maximize CPU utilization.
  - When the currently executing process must wait (e.g. for I/O completion), the OS scheduler intervenes, suspends the process, and switches CPU execution to another ready process.
  - On multicore systems, this principle extends across all parallel cores simultaneously.

--------------------------------------------------------------------------------
Slide 6: Alternating Sequence of CPU and I/O Bursts
--------------------------------------------------------------------------------
• Silberschatz Figure 5.1: The CPU-I/O Burst Cycle:
  - Process execution consists of alternating cycles of CPU computation (CPU burst) and waiting for I/O completion (I/O burst).
  - An execution cycle begins with a CPU burst, followed by an I/O burst, followed by another CPU burst:

    +------------------------------------------+
    | CPU burst: load, store, add, store, read |
    +------------------------------------------+
                         |
                         v
    +------------------------------------------+
    | I/O burst: wait for I/O                  |
    +------------------------------------------+
                         |
                         v
    +------------------------------------------+
    | CPU burst: store, increment, write       |
    +------------------------------------------+
                         |
                         v
    +------------------------------------------+
    | I/O burst: wait for I/O                  |
    +------------------------------------------+
  - CPU burst time distribution is a primary factor in designing efficient scheduling algorithms.

--------------------------------------------------------------------------------
Slide 7: The CPU Scheduler
--------------------------------------------------------------------------------
• Short-Term Scheduler:
  - Selects from among the processes residing in memory in the ready queue and allocates the CPU to one of them.
• Ready Queue Organization:
  - Implemented as a FIFO queue, priority queue, balanced binary search tree, or unordered linked list.
  - Queue records are Process Control Blocks (PCBs).

--------------------------------------------------------------------------------
Slide 8 & 9: Preemptive vs. Non-Preemptive Scheduling
--------------------------------------------------------------------------------
• Scheduling decisions occur under four specific state transitions:
  1. Running State -> Waiting State (e.g., process invokes I/O or wait())
  2. Running State -> Ready State (e.g., timer interrupt or higher-priority interrupt occurs)
  3. Waiting State -> Ready State (e.g., completion of I/O or arrival of an event)
  4. Running State -> Terminated (e.g., process calls exit())

• Classification:
  - **Non-Preemptive (Cooperative) Scheduling**:
    * Scheduling ONLY occurs under conditions (1) and (4).
    * Once a process is allocated the CPU, it keeps the CPU until it voluntarily releases it (by requesting I/O or terminating).
    * Examples: Windows 3.x.
  - **Preemptive Scheduling**:
    * Scheduling occurs under conditions (2) and (3) as well as (1) and (4).
    * The OS can forcibly preempt the currently executing process when its time quantum expires or a higher-priority process arrives.
    * Examples: Windows 95 onwards, Linux, macOS, Unix.

• Challenges of Preemptive Scheduling:
  - Race conditions on shared user memory and shared kernel data structures.
  - Preemption while executing in kernel mode requires kernel synchronization (mutex locks, spinlocks) to ensure data consistency.

--------------------------------------------------------------------------------
Slide 10 & 11: The Dispatcher & Dispatch Latency
--------------------------------------------------------------------------------
• Role of the Dispatcher:
  - The module that gives control of the CPU to the process selected by the short-term scheduler.
  - Functions performed:
    1. Switching context (saving old PCB, restoring new PCB).
    2. Switching from kernel mode to user mode (setting mode bit to 1).
    3. Jumping to the proper instruction address in the user program to resume execution.
• Dispatch Latency:
  - The exact amount of elapsed time required for the dispatcher to stop one process and start another running.

• Silberschatz Figure 5.3: Dispatch Latency Timeline:

  Process P0                  Dispatcher / Kernel              Process P1
  -----------------------------------------------------------------------
  Executing
      |
  [ Interrupt / Syscall ]
      |
      +---------------------> Save state into PCB_0
                              |
                              | <--- DISPATCH LATENCY --->
                              |
                              Restore state from PCB_1 ------> Executing

--------------------------------------------------------------------------------
Slide 12 & 13: Scheduling Criteria & Optimization Goals
--------------------------------------------------------------------------------
• Key Metrics:
  1. CPU Utilization: Percentage of time the CPU is actively performing work (typically 40% to 90%).
  2. Throughput: Number of processes completed per unit of time (e.g. 10 processes/second).
  3. Turnaround Time: Total elapsed time from process submission to process completion (Sum of: memory wait + ready queue wait + CPU execution + I/O execution).
  4. Waiting Time: Total cumulative time a process spends waiting in the ready queue.
  5. Response Time: Elapsed time from submission of a request until the first response is produced (critical for interactive/time-sharing systems).

• Optimization Criteria:
  - Maximize: CPU Utilization, Throughput.
  - Minimize: Turnaround Time, Waiting Time, Response Time.

--------------------------------------------------------------------------------
Slide 14, 15, 16, 17 & 18: First-Come, First-Served (FCFS) Scheduling
--------------------------------------------------------------------------------
• Principles:
  - The simplest scheduling algorithm: The process that requests the CPU first is allocated the CPU first using a FIFO ready queue.
  - Strictly non-preemptive.

• Example 1 (Arrival order: P1, P2, P3 at time t = 0):
  Process   Burst Time
  P1        24 ms
  P2        3 ms
  P3        3 ms

  Gantt Chart:
  +---------------------------------------------+---------+---------+
  |                     P1                      |   P2    |   P3    |
  +---------------------------------------------+---------+---------+
  0                                            24        27        30

  - Waiting Time:
    * Waiting time for P1 = 0 ms
    * Waiting time for P2 = 24 ms
    * Waiting time for P3 = 27 ms
  - Average Waiting Time:
    * (0 + 24 + 27) / 3 = 51 / 3 = 17.0 ms

• Example 2 (Arrival order: P2, P3, P1 at time t = 0):
  Gantt Chart:
  +---------+---------+---------------------------------------------+
  |   P2    |   P3    |                     P1                      |
  +---------+---------+---------------------------------------------+
  0         3         6                                            30

  - Waiting Time:
    * Waiting time for P1 = 6 ms
    * Waiting time for P2 = 0 ms
    * Waiting time for P3 = 3 ms
  - Average Waiting Time:
    * (6 + 0 + 3) / 3 = 9 / 3 = 3.0 ms

• The Convoy Effect:
  - A major disadvantage of FCFS where short I/O-bound processes become queued behind a single long CPU-bound process.
  - While the long process holds the CPU, all I/O devices sit idle.
  - When the long process finally yields for I/O, all short processes quickly finish CPU bursts and queue up at the I/O device, leaving the CPU idle.
  - Results in lower CPU and device utilization.

--------------------------------------------------------------------------------
Slide 19, 20, 21 & 22: Shortest-Job-First (SJF) Scheduling (Non-Preemptive)
--------------------------------------------------------------------------------
• Principles:
  - Associates with each process the length of its next CPU burst.
  - The CPU is assigned to the process with the smallest CPU burst time.
  - If two processes have equal burst times, FCFS is used as a tie-breaker.
  - **Optimality**: SJF is provably optimal because it generates the minimum average waiting time for a given set of stationary processes.

• Numerical Example (All arrive at time t = 0):
  Process   Burst Time
  P1        6 ms
  P2        8 ms
  P3        7 ms
  P4        3 ms

  Scheduling Order based on shortest burst: P4 (3) -> P1 (6) -> P3 (7) -> P2 (8)

  Gantt Chart:
  +---------+---------------+-------------------+---------------------+
  |   P4    |      P1       |        P3         |         P2          |
  +---------+---------------+-------------------+---------------------+
  0         3               9                  16                    24

  - Waiting Times:
    * P4 = 0 ms
    * P1 = 3 ms
    * P3 = 9 ms
    * P2 = 16 ms
  - Average Waiting Time:
    * (0 + 3 + 9 + 16) / 4 = 28 / 4 = 7.0 ms
  - Comparison with FCFS:
    * Under FCFS (order P1, P2, P3, P4):
      Waiting times: P1 = 0, P2 = 6, P3 = 14, P4 = 21.
      Average waiting time = (0 + 6 + 14 + 21) / 4 = 41 / 4 = 10.25 ms.
    * SJF achieves 7.0 ms vs. 10.25 ms.

--------------------------------------------------------------------------------
Slide 23: Preemptive SJF / Shortest-Remaining-Time-First (SRTF)
--------------------------------------------------------------------------------
• Concept:
  - Preemptive version of SJF with dynamic arrival times.
  - When a new process arrives with a CPU burst shorter than the remaining execution time of the currently running process, the current process is preempted.

• Numerical Problem:
  Process   Arrival Time   Burst Time
  P1        0 ms           8 ms
  P2        1 ms           4 ms
  P3        2 ms           9 ms
  P4        3 ms           5 ms

• Step-by-Step Scheduling Timeline:
  - t = 0: Only P1 is available. P1 begins executing (burst = 8).
  - t = 1: P2 arrives with burst = 4.
    * P1 has remaining burst = 8 - 1 = 7 ms.
    * Since P2 (4 ms) < P1 remaining (7 ms), P1 is preempted.
    * P2 is dispatched to the CPU.
  - t = 2: P3 arrives (burst = 9). P2 has remaining burst = 3 ms. P2 continues.
  - t = 3: P4 arrives (burst = 5). P2 has remaining burst = 2 ms. P2 continues.
  - t = 5: P2 completes execution.
    * Active processes in Ready Queue:
      - P1 (remaining = 7 ms)
      - P3 (remaining = 9 ms)
      - P4 (remaining = 5 ms)
    * Shortest remaining is P4 (5 ms). P4 is dispatched.
  - t = 10: P4 completes execution.
    * Active processes: P1 (7 ms), P3 (9 ms).
    * Shortest is P1 (7 ms). P1 resumes execution.
  - t = 17: P1 completes execution.
    * Only P3 remains (9 ms). P3 is dispatched.
  - t = 26: P3 completes execution.

• Gantt Chart:
  +-------+---------------+-------------------+-----------------------+---------------------+
  |  P1   |      P2       |        P4         |          P1           |         P3          |
  +-------+---------------+-------------------+-----------------------+---------------------+
  0       1               5                  10                      17                    26

• Waiting Time Calculations:
  - Waiting Time = Completion Time - Arrival Time - Burst Time
  - P1: Completion = 17, Arrival = 0, Burst = 8 -> Wait = 17 - 0 - 8 = 9 ms
        (Alternatively: Waited from t=1 to t=10: 10 - 1 = 9 ms)
  - P2: Completion = 5, Arrival = 1, Burst = 4  -> Wait = 5 - 1 - 4 = 0 ms
        (Ran immediately at t=1: 1 - 1 = 0 ms)
  - P3: Completion = 26, Arrival = 2, Burst = 9 -> Wait = 26 - 2 - 9 = 15 ms
        (Waited from t=2 to t=17: 17 - 2 = 15 ms)
  - P4: Completion = 10, Arrival = 3, Burst = 5 -> Wait = 10 - 3 - 5 = 2 ms
        (Waited from t=3 to t=5: 5 - 3 = 2 ms)

• Average Waiting Time:
  - Sum of waiting times = 9 + 0 + 15 + 2 = 26 ms
  - Average Waiting Time = 26 / 4 = 6.5 ms

--------------------------------------------------------------------------------
Slide 4: Priority Scheduling Concepts
--------------------------------------------------------------------------------
• Definition:
  - An integer priority number is associated with each process.
  - The CPU is allocated to the process with the highest priority.
  - Conventions:
    * In standard Silberschatz text: Smallest integer = Highest priority.
    * Note: Some systems (and certain problem formulations) define largest integer = highest priority. Always verify the convention used.
• Execution Modes:
  - **Non-Preemptive**: Once the CPU is given to a process, it runs to completion (or yields for I/O).
  - **Preemptive**: If a newly arrived process has a higher priority than the currently running process, the current process is immediately preempted.
• Relationship with SJF:
  - Shortest-Job-First (SJF) is simply a special case of priority scheduling where priority $p$ is the inverse of the predicted next CPU burst length ($p = 1 / \tau$).
• Major Problem: Starvation (Indefinite Blocking):
  - A low-priority process can be left waiting indefinitely in the ready queue if a steady stream of higher-priority processes continuously arrives.
  - Real-world case: When MIT's IBM 7094 was shut down in 1973, a low-priority process submitted in 1967 was discovered still waiting to run.
• Solution: **Aging**:
  - Gradually increase the priority of processes that wait in the system for long durations (e.g., increase priority by 1 every 15 minutes) until the process eventually achieves high enough priority to execute.

--------------------------------------------------------------------------------
Slide 5: Example of Non-Preemptive Priority Scheduling
--------------------------------------------------------------------------------
• Convention: Smallest integer = Highest priority (1 is highest).
• Process Table (All arrive at time t = 0):
  Process   Burst Time   Priority
  P1        10 ms        3
  P2        1 ms         1  (Highest)
  P3        2 ms         4
  P4        1 ms         5  (Lowest)
  P5        5 ms         2

• Priority Ordering:
  P2 (Pri 1) -> P5 (Pri 2) -> P1 (Pri 3) -> P3 (Pri 4) -> P4 (Pri 5)

• Gantt Chart:
  +---------+---------------+-----------------------------+---------+---------+
  |   P2    |      P5       |             P1              |   P3    |   P4    |
  +---------+---------------+-----------------------------+---------+---------+
  0         1               6                            16        18        19

  - P1: 6 ms
  - P2: 0 ms

  - P4: 18 ms

• Average Waiting Time:
  - Sum = 6 + 0 + 16 + 18 + 1 = 41 ms
  - Average Waiting Time = 41 / 5 = 8.2 ms

Slide 6: Example of Preemptive Priority Scheduling
--------------------------------------------------------------------------------
• Convention: Higher number = Higher priority (5 is highest).
• Process Table:
  Process   Arrival Time   Burst Time   Priority
  P1        0 ms           4 ms         2
  P2        1 ms           3 ms         3
  P3        2 ms           1 ms         4
  P4        3 ms           5 ms         5  (Highest)
  P5        4 ms           2 ms         5  (Highest)

• Step-by-Step Scheduling Timeline:
  - t = 0: Only P1 is present (pri 2). P1 begins execution.
  - t = 1: P2 arrives (pri 3). Since 3 > 2, P1 is preempted (P1 remaining = 4 - 1 = 3 ms).
    P2 begins execution.
  - t = 2: P3 arrives (pri 4). Since 4 > 3, P2 is preempted (P2 remaining = 3 - 1 = 2 ms).
    P3 begins execution.
  - t = 3: P3 finishes its 1 ms burst and terminates at t = 3.
    P4 arrives (pri 5). P4 begins execution.
  - t = 4: P5 arrives (pri 5). Since P4 and P5 have equal priority (5), FCFS tie-breaking keeps P4 running.
  - t = 8: P4 completes its 5 ms burst and terminates at t = 8.
    Highest priority among ready processes: P5 (pri 5, burst 2 ms). P5 runs from 8 to 10.
  - t = 10: P5 completes and terminates at t = 10.
    Ready processes: P2 (pri 3, remaining 2 ms) and P1 (pri 2, remaining 3 ms).
    P2 has higher priority (3 > 2), so P2 resumes from 10 to 12.
  - t = 12: P2 completes and terminates at t = 12.
    P1 resumes and runs from 12 to 15.
  - t = 15: P1 completes.

• Gantt Chart:
  +-------+-------+-------+-------------------+-----------+-----------+---------------+
  |  P1   |  P2   |  P3   |        P4         |    P5     |    P2     |      P1       |
  +-------+-------+-------+-------------------+-----------+-----------+---------------+
  0       1       2       3                   8          10          12              15

• Waiting Times:
  - Waiting Time = Completion Time - Arrival Time - Burst Time
  - P1: Completion = 15, Arrival = 0, Burst = 4 -> Wait = 15 - 0 - 4 = 11 ms
        (Waited: 12 - 1 = 11 ms)
  - P2: Completion = 12, Arrival = 1, Burst = 3 -> Wait = 12 - 1 - 3 = 8 ms
        (Waited: [2 to 10] = 8 ms)
  - P3: Completion = 3,  Arrival = 2, Burst = 1 -> Wait = 3 - 2 - 1 = 0 ms
  - P4: Completion = 8,  Arrival = 3, Burst = 5 -> Wait = 8 - 3 - 5 = 0 ms
  - P5: Completion = 10, Arrival = 4, Burst = 2 -> Wait = 10 - 4 - 2 = 4 ms
        (Waited: [4 to 8] = 4 ms)

• Average Waiting Time:
  - Sum = 11 + 8 + 0 + 0 + 4 = 23 ms
  - Average Waiting Time = 23 / 5 = 4.6 ms

Slide 7, 8 & 9: Round-Robin (RR) Scheduling
--------------------------------------------------------------------------------
• Design Principles:
  - Designed specifically for time-sharing / interactive multitasking systems.
  - Preemptive algorithm based on FCFS principles.
  - Defines a small unit of time called a **Time Quantum** (or time slice), typically 10 to 100 milliseconds.
  - Ready queue is managed as a circular FIFO queue.
  - Scheduler allocates the CPU to each process in FIFO order for up to 1 time quantum.
  - If process finishes before quantum expires, it releases CPU voluntarily.
  - If process is still running at the end of the quantum, a timer interrupt preempts it, and the process is appended to the tail of the ready queue.

• Numerical Example (All arrive at time t = 0, Quantum q = 4 ms):
  Process   Burst Time
  P1        24 ms
  P2        3 ms
  P3        3 ms

  - Execution:
    * t = 0: P1 runs for 4 ms (remaining = 20 ms). Put at tail of queue.
    * t = 4: P2 runs for 3 ms (needs only 3 ms). Terminates at t = 7.
    * t = 7: P3 runs for 3 ms (needs only 3 ms). Terminates at t = 10.
    * t = 10 onwards: Only P1 remains in ready queue. P1 executes in remaining 4 ms quanta until completion at t = 30.

• Gantt Chart:
  +---------+------+------+---------+---------+---------+---------+---------+
  |   P1    |  P2  |  P3  |   P1    |   P1    |   P1    |   P1    |   P1    |
  +---------+------+------+---------+---------+---------+---------+---------+
  0         4      7     10        14        18        22        26        30

• Waiting Times:
  - P1: Runs [0 to 4], waits [4 to 10], then runs to finish. Wait = 10 - 4 = 6 ms.
  - P2: Waits [0 to 4]. Wait = 4 ms.
  - P3: Waits [0 to 7]. Wait = 7 ms.

• Average Waiting Time:
  - Sum = 6 + 4 + 7 = 17 ms
  - Average Waiting Time = 17 / 3 = 5.66 ms

• Round-Robin Performance Analysis:
  - Maximum Waiting Bound:
    * If there are $n$ processes in the ready queue and time quantum is $q$:
    * Each process gets $1/n$ of the CPU time in chunks of at most $q$.
    * No process waits longer than $(n - 1) \times q$ time units until its next time slice.
  - Impact of Time Quantum $q$:
    * If $q$ is extremely large ($\to \infty$): RR degenerates into simple FCFS.
    * If $q$ is extremely small (e.g. 1 $\mu$s): Produces the illusion of processor sharing (each of $n$ processes running on a CPU at $1/n$ speed), BUT excessive context switches consume nearly all CPU cycles in dispatch latency overhead.
  - Practical Rule of Thumb:
    * About 80% of CPU bursts should be shorter than the time quantum $q$ to avoid frequent preemptions for typical interactive tasks.

--------------------------------------------------------------------------------
Slide 4 & 5: Multilevel Queue (MLQ) Scheduling
--------------------------------------------------------------------------------
• Motivation:
  - In situations where processes can be easily classified into distinct groups with fundamentally different response-time requirements, a single ready queue is inadequate.
  - Common Partitioning:
    * **Foreground Processes**: Interactive programs requiring low response time.
    * **Background Processes**: Batch jobs where response time is secondary to throughput.
• Permanent Assignment:
  - Processes are permanently assigned to one specific queue upon creation, typically based on memory size, process priority, or process type.
• Intra-Queue Scheduling:
  - Each individual queue maintains its own independent scheduling algorithm:
    * Foreground Queue: Round-Robin (RR) scheduling to provide responsive interactive feedback.
    * Background Queue: First-Come, First-Served (FCFS) scheduling to minimize context-switch overhead for batch computations.

• Silberschatz Figure 5.6: Multilevel Queue Priority Hierarchy:

    HIGHEST PRIORITY
       |   +-------------------------------------------+
       |   | System Processes                          |
       |   +-------------------------------------------+
       |   | Interactive Processes                     |
       |   +-------------------------------------------+
       |   | Interactive Editing Processes             |
       |   +-------------------------------------------+
       |   | Batch Processes                           |
       |   +-------------------------------------------+
       v   | Student Processes                         |
    LOWEST PRIORITY

• Inter-Queue Scheduling Policies:
  1. Fixed-Priority Preemptive Scheduling:
     - Each queue has absolute priority over lower-priority queues.
     - No process in a lower-priority queue (e.g. batch) can execute unless all higher-priority queues (system, interactive, editing) are completely empty.
     - Preemption: If a batch process is executing and an interactive process enters the ready queue, the batch process is immediately preempted.
     - Major drawback: High risk of **Starvation** for processes in low-priority queues if higher queues remain continuously populated.
  2. Time-Sliced Scheduling:
     - Each queue receives a predetermined fraction of the CPU time, which it distributes among its member processes.
     - Example: 80% of CPU time allocated to foreground queue (using RR), 20% allocated to background queue (using FCFS).
     - Prevents indefinite starvation.

--------------------------------------------------------------------------------
Slide 6, 7 & 8: Multilevel Feedback Queue (MLFQ) Scheduling
--------------------------------------------------------------------------------
• Core Innovation:
  - Unlike standard Multilevel Queue where processes are permanently stuck in their initial queue, Multilevel Feedback Queue allows processes to **migrate between different queues**.
  - Dynamically adapts to the runtime CPU-burst characteristics of processes.
  - Implements **Aging** to prevent starvation.

• Defining Parameters of an MLFQ Scheduler:
  An MLFQ scheduler is strictly defined by the following five parameters:
  1. The number of queues.
  2. The scheduling algorithm for each individual queue.
  3. The method used to determine when to upgrade (promote) a process to a higher-priority queue.
  4. The method used to determine when to demote a process to a lower-priority queue.
  5. The method used to determine which queue a newly arrived process will enter.

• Silberschatz Figure 5.7: Concrete 3-Queue MLFQ Architecture:

            [ New Process Enters ]
                      |
                      v
      +-------------------------------+
      | Queue 0 (Q0): RR, Quantum = 8 |
      +---------------+---------------+
                      | (If not completed within 8 ms)
                      v
      +-------------------------------+
      | Queue 1 (Q1): RR, Quantum = 16|
      +---------------+---------------+
                      | (If not completed within 16 ms)
                      v
      +-------------------------------+
      | Queue 2 (Q2): FCFS            |
      +-------------------------------+

• Execution & Demotion Rules in this Example:
  1. Queue 0 ($Q_0$):
     - Uses Round-Robin with a time quantum of 8 milliseconds.
     - A newly created process always enters $Q_0$.
     - When dispatched, it is granted up to 8 ms of CPU time.
     - If it finishes within 8 ms or yields for I/O, it leaves the CPU cleanly.
     - If it consumes its full 8 ms without yielding (indicating it is CPU-bound), it is preempted and demoted to the tail of Queue 1 ($Q_1$).
  2. Queue 1 ($Q_1$):
     - Uses Round-Robin with a time quantum of 16 milliseconds.
     - Processes in $Q_1$ are scheduled ONLY when $Q_0$ is completely empty.
     - When dispatched, a process is granted up to 16 ms.
     - If it does not complete within 16 ms, it is preempted and demoted to the tail of Queue 2 ($Q_2$).
  3. Queue 2 ($Q_2$):
     - Uses First-Come, First-Served (FCFS) scheduling.
     - Executes ONLY when both $Q_0$ and $Q_1$ are completely empty.
  4. Preemption between Queues:
     - An arrival in $Q_0$ immediately preempts any running process in $Q_1$ or $Q_2$.
     - An arrival in $Q_1$ immediately preempts any running process in $Q_2$.

• Promotion (Aging) Policy:
  - If a CPU-bound process waits too long in $Q_2$ without CPU service, an aging timer triggers.
  - The process is promoted upward to $Q_1$ or $Q_0$, guaranteeing that long-running jobs eventually make forward progress and cannot starve.

Slide 3, 4 & 5: What is a Shell? & Shell Variants
--------------------------------------------------------------------------------
• Definition:
  - The shell is the command-line interpreter (CLI) in Unix/Linux operating systems.
  - Acts as an intermediary layer between the user and the kernel:
    [ User / Terminal ] <---> [ Shell Interpreter ] <---> [ OS Kernel ] <---> [ Hardware ]
  - Reads commands entered by the user, parses arguments, and requests the kernel to spawn processes or execute system programs, user binaries, or shell scripts.

• Command Syntax & Parsing:
  syntax: command [arg1] [arg2] ... [argn]
  - Square brackets `[]` signify optional arguments.
  - When the user presses Enter (Carriage Return), the shell reads the entire line and tokenizes it into:
    1. Command name
    2. Flags / Options (e.g. `-l`, `-a`)
    3. Target arguments (e.g. filenames, paths)
  - Executable Lookup:
    * If a path is specified (`./myscript.sh` or `/bin/ls`), the shell directly accesses that file.
    * If only a name is given (`ls`), the shell traverses the directories listed in the `$PATH` environment variable in order from left to right until the executable binary is found.

• Survey of Common Unix/Linux Shells:
  1. `sh` (Bourne Shell): Original shell developed by Stephen Bourne at AT&T Bell Labs.
  2. `csh` / `tcsh` (C Shell / TENEX C Shell): Created by Bill Joy with syntax modeled on the C programming language.
  3. `ksh` (Korn Shell): Developed by David Korn combining features of Bourne shell and C shell.
  4. `bash` (Bourne-Again Shell): Developed by the GNU project; the standard default shell across modern Linux distributions.
  - To display active login shell:
    $ echo $SHELL
    Output: /bin/bash

--------------------------------------------------------------------------------
Slide 6, 7 & 8: Environment Variables vs. Shell Variables
--------------------------------------------------------------------------------
• Difference in Scope & Inheritance:
  1. **Shell Variables**:
     - Local exclusively to the current shell process in which they are defined.
     - NOT inherited by child processes, spawned scripts, or subshells.
     - Used for ephemeral, local shell state.
  2. **Environment Variables**:
     - Global variables exported into the shell's environment block.
     - Automatically inherited by all child processes and subshells created by that shell.
     - By convention, named in uppercase letters (e.g., `PATH`, `USER`).

• Standard Environment Variables:
  - `SHELL`: Path to the active command-line interpreter (e.g., `/bin/bash`).
  - `TERM`: Terminal emulation mode for terminal capabilities (e.g., `xterm-256color`).
  - `USER`: Username of the currently authenticated session.
  - `PWD`: Current working directory absolute path.
  - `OLDPWD`: Previous working directory before the last `cd` command (enables `cd -`).
  - `PATH`: Colon-separated list of search directories for executable programs.

• Common Bash-Specific Shell Variables:
  - `BASHOPTS`: Comma-separated list of active bash options (e.g. `checkwinsize:cmdhist`).
  - `BASH_VERSION`: Human-readable version string (e.g., `5.0.17(1)-release`).
  - `BASH_VERSINFO`: Multi-element array containing major, minor, patch levels.

Slide 14, 15, 16 & 17: The Cron Scheduling Daemon
--------------------------------------------------------------------------------
• Overview:
  - `cron` is a Unix/Linux background daemon (`crond` / `cron.service`) that automatically launches tasks at scheduled times and dates.
  - Starts automatically at boot time via systemd.
  - Verifying daemon status:
    $ sudo systemctl status cron.service
    Active: active (running)

• Crontab File Management:
  - `crontab -l`: Lists all scheduled cron jobs for the current user.
  - `crontab -e`: Opens the crontab file in the default text editor to add, edit, or delete jobs.
  - `crontab -r`: Deletes the current user's entire crontab schedule.

• Crontab 5-Field Time Specification:
  +----------------- Minute (0 - 59)
  | +--------------- Hour (0 - 23, 24-hour clock)
  | | +------------- Day of the Month (1 - 31)
  | | | +----------- Month of the Year (1 - 12)
  | | | | +--------- Day of the Week (0 - 6, where 0 = Sunday)
  | | | | |
  * * * * *  /path/to/command_or_script.sh

• Practical Scheduling Expressions:
  1. `5 0 * 8 *`
     - Executes at 00:05 (12:05 AM) every day during the month of August.
  2. `5 4 * * 6`
     - Executes at 04:05 AM on every Saturday.
  3. `0 22 * * 1-5`
     - Executes at 22:00 (10:00 PM) every weekday from Monday through Friday.
  4. `*/1 * * * *` (or `* * * * *`)
     - Executes once every minute.

Q1. You are designing an Operating System for a supercomputer used exclusively for
weather forecasting (a scientific mainframe) and another for a home entertainment tablet.
Contrast the "Operating System Goals" for these two systems. How does the definition of
"efficiency" differ between them?
Answer: Mainframe (Weather Supercomputer): The primary goal is Resource Utilization.
Since the hardware is expensive and powerful, the OS must ensure the CPU, memory, and I/O
channels are busy constantly to maximize throughput. "Efficiency" here means executing the
maximum number of calculations per second.
Tablet (Home Entertainment): The primary goal is User Convenience and Ease of Use. The
OS focuses on a responsive UI and battery life rather than keeping the CPU 100% busy.
"Efficiency" here means low power consumption and smooth interaction, even if the CPU sits idle
waiting for user input.

Q2. Why is the Operating System described as "Interrupt Driven"? What would happen to
the system's responsiveness if interrupts were disabled entirely?
Answer: Interrupt Driven: The OS sits idle until something happens. Events (keystrokes, disk
completion, network packets, system calls) are all signaled via interrupts. The OS wakes up,
handles the event, and goes back to waiting or running a user process.
Consequence of Disabling: If interrupts were disabled, the OS could not react to any external
input. The keyboard would freeze, the mouse wouldn't move, and disk operations wouldn't notify
the CPU upon completion. The system would effectively appear "hung" or unresponsive to the
user.

Q3. "A user program cannot directly access hardware." If a text editor needs to save a file
to the disk, explain the mechanism it uses to bypass this restriction securely. What role does
the Dual-Mode (User/Kernel) architecture play here?
Answer: The text editor issues a System Call (e.g., write()). This is a special instruction that
triggers a software interrupt (Trap).
Dual-Mode Role:
● The trap switches the CPU from User Mode to Kernel Mode.
● The OS (now in Kernel Mode) validates the request (permissions, path).
● The OS performs the hardware operation on the disk.
● The OS switches back to User Mode and returns control to the text editor.
● This ensures the user program never touches the hardware directly, preventing errors or
malicious access.

Lecture 2 - Computer-System Architecture, Operating-System Structure & Operations

Q1. In a Symmetric Cluster, two nodes try to write to the same student record on the shared
Storage Area Network (SAN) at the exact same instant. What mechanism prevents data
corruption here? Why isn't a simple local semaphore sufficient?
Answer: Since the nodes are separate computers, they do not share local memory. A local
semaphore on Node A is invisible to Node B. Thus, the system must use a Distributed Lock
Manager (DLM).
Mechanism: The DLM coordinates access control across the network, ensuring that only one node
holds the "write lock" for a specific shared resource on the SAN at any given time.

Q2. In a multiprogrammed system, multiple jobs reside in memory simultaneously. If the
system has 8GB of RAM but the active jobs require 12GB total, what mechanism allows the
system to continue operating? Briefly explain Swapping/Virtual Memory.

Answer: Constraint: Physical memory is finite. Not all jobs can fit in RAM at once.
Mechanism: The OS uses Swapping or Virtual Memory.
Operation: Processes not currently executing are swapped out to the hard disk (backing store),
freeing up RAM for the active process. When the swapped-out process is needed again, it is loaded
back into memory. This allows the execution of processes larger than physical memory.

Q3. Scenario: What would happen if the Mode Bit stuck at '0' due to a hardware glitch while
a user program was running? Analyze the risk to system stability and security.
Answer: State: If the bit sticks at 0, the CPU remains in Kernel Mode permanently.
Risk: The currently running user program would have unrestricted access to the entire
system.
Consequence: It could read other users' passwords from memory, wipe the hard disk, or overwrite
the OS code. The system loses all protection boundaries, likely leading to a crash or security
breach.

Q4. Modern CPUs often support more than just two modes. What is the purpose of the VMM
(Virtual Machine Manager) Mode? How does it relate to "Guest VMs"?
Answer: In virtualization, a host OS runs multiple guest operating systems. CPUs support a
dedicated mode for the Virtual Machine Manager (Hypervisor).
This allows the VMM to have higher privileges than the Guest OS kernels (which think they are
in kernel mode but are actually being managed) without needing full physical root access for every
operation, improving virtualization efficiency and security.

Q1. A headless server (a computer without a monitor or keyboard) in a data center crashes
due to a memory error. Since there is no screen to display an error message, which OS service
is responsible for handling this, and how does the administrator eventually find out what
happened?
Answer: The Error Detection service is responsible. When the error occurs, the OS generates a
core dump or writes the error details to a system log file.

The administrator accesses these logs later (via network or remote shell) to diagnose the issue.
Without this service, the system would simply freeze with no diagnostic trail.

Q2. Early OSes were written in Assembly. Modern OSes (like Linux/Windows) are written
mostly in C/C++. Give two reasons for this shift. Is there any part of the OS still written in
Assembly?
Answer: C code is portable. C code can be recompiled for different CPU architectures (x86,
ARM). Assembly is specific to one CPU family.
It is also highly maintainable. High-level code is easier to read, write, and debug.
Yes, small critical sections like the interrupt handlers and device drivers are still written in
Assembly for maximum speed and direct hardware control.

Q3. Two processes need to exchange data. The OS provides Shared Memory and Message
Passing. Which method would you choose for exchanging small amounts of status data
between two computers across a network? Justify.
Answer: Message Passing.
Justification: Shared Memory is difficult or impossible to implement across different physical
computers (distributed systems). Message passing is designed for communication, handling the
packet formatting and synchronization required for network data transfer.

Q4. How does the "Process Lifecycle" in a mobile OS (like Android) differ from a traditional
desktop OS regarding background processes? Why might the OS terminate a background
process without the user explicitly closing it?
Answer: Mobile devices have limited memory and battery compared to desktops. While desktop
systems typically use swapping (virtual memory) to manage overflow, mobile OSes generally do
not support swapping.
Instead, when memory runs low, the mobile OS automatically terminates background processes (that are not visible to the user) to reclaim memory for the foreground application. The state is
saved to flash memory to be restored later.

Q5. System Calls: Explain the relationship between fork() and exec(). Task: Why do most
programs call exec() immediately after fork()? What happens to the memory of the child
process during exec()?
Answer: fork() creates a duplicate copy of the parent process. exec() replaces the memory space
of a process with a new program. Programs call them in sequence to run a different program. For
example, the Shell forks a copy of itself, then the child calls exec() to become the "ls" command.
During exec(), the child's text, data, and stack segments are completely destroyed and overwritten
by the new program loaded from the disk.

Q6. What is "Cascading Termination"? If a user kills the main BASH shell process, what
happens to the background commands running under it in an OS that enforces cascading
termination?
Answer: Cascading Termination is a policy where the OS does not allow a child process to exist
if its parent has terminated.
If the BASH shell (Parent) is killed, the OS detects its children. The OS automatically initiates
termination for all children, grandchildren, and further descendants of that shell. All background
commands running under it are forcibly closed.

Lecture 5 - Process Creation and Termination, System calls for process management

Q1. You are optimizing a system where a process needs to create a child that immediately
calls exec() to run a new program. Would you use fork() or vfork()? Justify your choice based
on memory overhead and performance.

Answer: vfork() is preferred in this specific scenario.
Justification:
● Standard fork(): Copies the parent's data space, heap, and stack to the child. If the child
immediately calls exec(), this copying is wasted effort because exec() replaces all of it
anyway.
● vfork() Optimization: It creates a child without copying the address space. The child
borrows the parent's memory until it calls exec(), making it significantly faster and more
memory-efficient for this specific pattern.

Q2. A server runs for months. You check the process table and see hundreds of "Zombie"
entries. Explain what a Zombie process is in terms of resource usage. Why is it a problem if
they accumulate?
Answer: A Zombie is a process that has terminated (exit()) but whose parent has not yet called
wait() to collect its status. They consume no CPU and almost no memory (text/data are freed).
They still occupy a slot in the Process Table (to store the PID and exit status). If zombies
accumulate, the system runs out of available PIDs, preventing new processes from starting.

Q3. "During I/O execution, the requesting process is typically blocked." Task: Why does the
OS block the process instead of letting it spin in a loop checking for data? How does this
improve "System Throughput"?
Answer: I/O devices are thousands of times slower than the CPU. Spinning (busy waiting) would
waste millions of CPU cycles doing nothing. By blocking the process (moving it to the Waiting
state), the OS frees the CPU.
The OS performs a Context Switch to run a different, ready process. This keeps the CPU busy
doing useful work for Process B while Process A waits for the disk, increasing overall system
throughput.

Lecture 7 - CPU Scheduling- FCFS Scheduling, SJF Scheduling
================================================================================

Q1. Analyze the "CPU-I/O Burst Cycle" and its significance in the context of
multiprogramming. How does the frequency distribution of CPU bursts influence the design
of scheduling algorithms?

Answer: To understand why CPU scheduling is necessary, one must first understand the lifecycle
of a process. Process execution is not a continuous block of calculation; rather, it consists of an
alternating cycle of CPU execution (CPU burst) and I/O wait (I/O burst).
In a system without multiprogramming, when a process encounters an I/O burst (like reading from
a file), the CPU sits idle, wasting valuable computational resources. The fundamental objective of
multiprogramming is to maximize CPU utilization by switching the CPU to another process
effectively during these wait times.
The frequency distribution of CPU bursts is critical for designing efficient schedulers. Empirical
measurements show that processes tend to have a vast number of short CPU bursts (I/O-bound
programs) and a small number of long CPU bursts (CPU-bound programs). A scheduling
algorithm must be designed to handle this curve effectively—balancing the needs of interactive
processes (short bursts) against computational heavyweights (long bursts) to ensure the system
remains responsive and efficient.

Q2. Differentiate between preemptive and non-preemptive scheduling by examining the
specific process state transitions that trigger a scheduling decision. Why is non-preemptive
scheduling considered "cooperative"?
Answer: CPU scheduling decisions occur at four specific transition points in a process's life:
1. When a process switches from running to waiting (e.g., an I/O request).
2. When a process switches from running to ready (e.g., an interrupt).
3. When a process switches from waiting to ready (e.g., I/O completion).
4. When a process terminates.

Non-preemptive scheduling occurs only under conditions 1 and 4. In this mode, once the CPU is
allocated to a process, that process keeps the CPU until it voluntarily releases it by terminating or
switching to a waiting state. It is "cooperative" because the scheduler waits for the process to yield.

Preemptive scheduling, on the other hand, can occur during conditions 2 and 3. Here, the OS can
forcibly remove a running process from the CPU to allocate it to a higher-priority task. This
approach is standard in modern operating systems (like Windows 95+ and Macintosh OS) to
ensure responsiveness, whereas older systems like Windows 3.x relied on non-preemptive methods

Q3. The "Dispatcher" is a distinct component from the scheduler. Elucidate the specific
responsibilities of the dispatcher and explain how "dispatch latency" impacts system
performance.
Answer: It is important to distinguish between selection and execution. The scheduler selects
which process should run next, but the dispatcher is the module that actually gives control of the
CPU to that selected process.
The dispatcher performs the low-level mechanics of the hand-over, which involves:
1. Switching context: Saving the state of the old process and loading the state of the new
one.
2. Switching to user mode: Transitioning from kernel mode back to user mode so the
application can run.
3. Jumping: Moving the instruction pointer to the proper location in the user program to
resume execution.
This process is not instantaneous. The time taken for the dispatcher to stop one process and start
another is called dispatch latency. This latency is pure overhead—no useful work is done during
this time. Therefore, minimizing dispatch latency is crucial; if it is too high, the system spends
more time shuffling processes than actually executing them.

Q4. The First-Come, First-Served (FCFS) algorithm is technically simple but can lead to the
"Convoy Effect." Analyze this phenomenon and explain why FCFS is generally considered
unsuitable for time-sharing systems.

Answer: FCFS is the simplest scheduling algorithm: processes are assigned the CPU in the exact
order they request it. It is non-preemptive, meaning once a process gains the CPU, it retains
control until it voluntarily terminates or waits for I/O.
The Convoy Effect occurs when a single CPU-bound process (a process with a very long CPU
burst) effectively "clogs" the system. Several shorter I/O-bound processes may get stuck waiting
behind this single long process. Instead of quickly executing their short bursts and returning to I/O,
they idle in the ready queue, leading to poor resource utilization and high average waiting times.
This characteristic makes FCFS problematic for time-sharing systems. In such environments, it
is critical that every user or process receives a share of the CPU at regular intervals to maintain
responsiveness. FCFS cannot guarantee this, as one process can monopolize the CPU for an
extended period, making the system appear unresponsive to other users.

Q5. Consider a set of processes 𝑃1, 𝑃2, 𝑃3 arriving at the same time (t=0) with burst times of
24ms, 3ms, and 3ms respectively. Compare the Average Waiting Time (AWT) if they are
scheduled using FCFS (order 𝑃1, 𝑃2, 𝑃3) versus FCFS (order 𝑃1, 𝑃2, 𝑃3). What does this
comparison reveal about the sensitivity of FCFS?
Answer:
This scenario highlights the extreme sensitivity of FCFS to arrival order.
•

Case 1 (𝑃1, 𝑃2, 𝑃3): 𝑃1 (24ms) runs first. 𝑃2 waits 24ms. 𝑃3 waits 27ms (24+3).

○ AWT = (0 + 24 + 27) / 3 = 17ms.
•

Case 2 (𝑃1, 𝑃2, 𝑃3): 𝑃2 (3ms) runs first. 𝑃3 waits 3ms. 𝑃1 waits 6ms (3+3).

○ AWT = (0 + 3 + 6) / 3 = 3ms .
The comparison reveals that the AWT under FCFS is not minimal and can vary substantially
depending on whether CPU-bound processes arrive before or after I/O-bound processes. A simple
reordering of the same tasks reduced the waiting time by over 80%, illustrating why FCFS is risky for systems with variable burst lengths.

Lecture 8 - CPU Scheduling Algorithms 2

Q1. Priority Scheduling assigns the CPU based on rank rather than arrival time. Explain the
convention used to define "highest priority" in most systems and discuss the critical problem
of "Starvation" inherent to this algorithm. How does "Aging" resolve this issue?
Answer: In Priority Scheduling, a priority number (integer) is associated with each process. The
convention typically followed is that a smaller integer denotes a higher priority; thus, the CPU is
allocated to the process with the smallest integer value.
The inherent weakness of this algorithm is indefinite blocking, also known as starvation. In a
heavily loaded system, a steady stream of higher-priority processes can prevent a low-priority
process from ever gaining access to the CPU. A low-priority task could literally wait indefinitely
without ever executing.
To solve this, schedulers implement a technique called Aging. This involves gradually increasing
the priority of a process as it sits in the wait queue. For example, if a process's priority number is
decremented (improved) every few minutes, it will eventually become the highest-priority process
in the system and be executed, regardless of new arrivals.

Q2. Conceptually, Shortest-Job-First (SJF) can be categorized as a specific type of Priority
Scheduling. Analyze the relationship between these two algorithms. What determines the
"priority" in an SJF context?
Answer: SJF is essentially a specific application of the general Priority Scheduling mechanism.
In standard priority scheduling, the priority is an arbitrary number assigned based on external
criteria (like user importance or payment).
In the case of SJF, the priority is internally derived from the process's characteristics. Specifically,
the priority is the inverse of the predicted next CPU burst time. The shorter the predicted burst, the
higher the priority (or the lower the priority value) the process is assigned. Therefore, SJF creates
an ordering where the "most important" jobs are simply the ones that can finish the quickest.

Q3. The performance of the Round Robin algorithm is highly sensitive to the size of the Time
Quantum. Contrast the system behavior when the quantum is "extremely large" versus
when it is "extremely small." What is the impact on context switching?
Answer: The choice of time quantum dictates the nature of the scheduler:
● Extremely Large Quantum: If the quantum is large enough to cover the longest CPU
burst in the system, the RR policy degenerates into a standard FCFS policy. The overhead
of round-robin management remains, but the benefit of responsiveness is lost.
● Extremely Small Quantum: If the quantum is too small, the system suffers from
excessive overhead. For example, if the quantum is 1 time unit and a process needs 10
units, the system must perform 9 context switches. Since a context switch takes time
(typically < 10 microseconds), performing them too frequently wastes significant CPU
time on administrative tasks rather than executing user code.
Thus, the quantum must be large enough relative to the context-switch time to be efficient, but
small enough to maintain interactivity.

Lecture 10 - CPU Scheduling Algorithms 3
================================================================================

Q1. How does the Multilevel Feedback Queue (MLFQ) scheduler improve upon the standard
Multilevel Queue approach? specifically, detail the five parameters that define an MLFQ
scheduler and explain how "aging" is implemented in this system.
Answer: The standard Multilevel Queue algorithm suffers from inflexibility because processes
are permanently assigned to a queue. The Multilevel Feedback Queue (MLFQ) improves upon
this by allowing processes to move between queues based on their behavior.
An MLFQ scheduler is defined by five key parameters:
1. The number of queues.
2. 2. The scheduling algorithm used for each queue.
3. 3. The method to determine when to upgrade a process to a higher-priority queue.
4. 4. The method to determine when to demote a process to a lower-priority queue.
5. 5. The method to determine which queue a process enters when it first needs service.

This flexibility allows the system to implement aging to prevent starvation. If a low-priority
process waits too long, it can be moved to a higher-priority queue. Conversely, processes that
consume too much CPU time (CPU-bound) can be demoted to lower-priority queues, leaving the
high-priority queues for interactive (I/O-bound) processes.

Q2. Consider a Multilevel Feedback Queue system with three queues: 𝑄0 (RR, 8ms
quantum), 𝑄1 (RR, 16ms quantum), and 𝑄2 (FCFS). Trace the path of a long CPU-bound
process entering this system and explain how preemption is handled between these queues.
Answer: In this specific MLFQ configuration, a new process enters 𝑄0 and is served on a
FirstCome, First-Served basis. When it gains the CPU, it receives a time quantum of 8 milliseconds.
If the process is CPU-bound and does not finish within this 8ms quantum, it is demoted to the tail
of 𝑄1. Once in $Q_1$, it waits until $Q_0$ is empty. When it eventually runs, it receives a larger
time quantum of 16 milliseconds. If it still fails to complete its burst within this 16ms allocation,
it is preempted again and demoted to $Q_2$, where it is processed using a standard FCFS
algorithm alongside other background tasks .
Preemption in this system is hierarchical. The scheduler prioritizes higher queues absolutely. If a
process arrives for $Q_1$, it will preempt a running process from $Q_2$. Furthermore, a process
running in $Q_1$ will itself be preempted if a new process arrives in $Q_0$, ensuring the system
remains responsive to new, short tasks.

Q1. Analyze the operational flow of a Shell when a user enters a command. specifically, how
does the shell distinguish between a "Shell Variable" and an "Environment Variable" in
terms of scope and inheritance?
Answer: When a user types a command, the shell acts as an interface between the user and the
kernel. It parses the input into tokens (command name, options, arguments) and locates the
executable—either in the current directory or by searching through the directories listed in the
$PATH variable.
A critical distinction in shell operation is variable management:

● Shell Variables: These are local to the specific shell instance where they are defined. They
are not passed down to child processes. They are often used for ephemeral data within a
script or session .
● Environment Variables: These are defined for the current shell but are inherited by any
child shells or processes spawned from it. This allows configuration data (like user
preferences or system paths) to be passed seamlessly to applications .
● Scope Transition: A shell variable can be promoted to an environment variable using the
export command (e.g., export MY_VAR="value"). Without export, a child shell (spawned
by typing bash) would not see the variable.

Q2. Explain the significance of the PATH environment variable. What specific problem does
it solve for the user, and how does the shell utilize it during command execution?
Answer: The PATH environment variable is a colon-separated list of directories that acts as a
roadmap for the shell.
Without PATH, a user would have to type the absolute path of every program they wanted to run
(e.g., /usr/bin/ls instead of just ls). The PATH variable solves this by automating the search. When
a command is entered, the shell iterates through the directories listed in PATH in order. It executes
the first matching executable it finds. This mechanism allows users to run system utilities and
custom scripts from any location in the file system without knowing their exact installation path.

# Chapter 1: Introduction to Operating Systems

**Textbook References**: [Silberschatz 10e, Ch. 1-2] • [Stallings 9e, Ch. 1-2] • [Stevens & Rago 3e, Ch. 1]

---

## 1.1 What is an Operating System?

An **Operating System (OS)** is a program that acts as an intermediary between a user of a computer and the computer hardware. [Silberschatz 10e, §1.1]

> **Silberschatz Definition**: "An operating system is a program that acts as an intermediary between a user of a computer and the computer hardware." [Silberschatz 10e, p. 3]

### Goals of an OS [Silberschatz 10e, §1.2]
1. **Execute user programs** and make solving user problems easier
2. **Convenience** — make the computer system easy to use
3. **Efficiency** — use computer hardware in an efficient manner
4. **Resource Management** — manage CPU, memory, I/O devices, files

> **Silberschatz**: "The operating system acts as a resource allocator and a control program." [Silberschatz 10e, §1.2.1]

### Why Study OS? [Silberschatz 10e, §1.3]
- Almost all code runs on top of an OS
- Understanding OS internals enables writing optimized, secure, high-performance software
- Knowledge of scheduling, memory management, concurrency is fundamental

> **Silberschatz**: "Only a small percentage of computer practitioners will be involved in the creation or modification of an operating system. However, almost all code runs on top of an operating system." [Silberschatz 10e, §1.3]

---

## 1.2 Computer System Organization

### Four Components of a Computer System [Silberschatz 10e, §1.2.2]
| Component | Role |
|-----------|------|
| **Hardware** | CPU, memory, I/O devices — basic computing resources |
| **Operating System** | Controls and coordinates hardware use among applications/users |
| **Application Programs** | Define how system resources solve user problems (compilers, browsers, DBs) |
| **Users** | People, machines, other computers issuing requests |

### Layered View [Silberschatz 10e, Fig. 1.1]
```
User Applications
       ↓
System Calls / User Interface (CLI, GUI, Batch)
       ↓
Operating System Services
  ├── Program Execution    ├── I/O Operations      ├── File Systems
  ├── Communications       ├── Resource Allocation ├── Accounting
  ├── Error Detection      ├── Protection & Security
       ↓
Hardware (CPU, Memory, I/O Devices)
```

> **Silberschatz Fig. 1.1**: "Abstract view of the components of a computer system" [Silberschatz 10e, Fig. 1.1]

---

## 1.3 Operating System Operations

### Interrupt-Driven Nature [Silberschatz 10e, §1.5]
Modern OS is **interrupt-driven** — sits idle waiting for events signaled by interrupts.

#### Interrupt Classification [Silberschatz 10e, §1.5.1]
```
Interrupt Event
    ├── Hardware Interrupt
    │     ├── Polling (CPU queries devices)
    │     └── Vectored (hardware provides offset into Interrupt Vector Table → ISR)
    └── Software Interrupt (Trap/Exception)
          ├── Error (division by zero, invalid memory access)
          └── System Call (user requests OS service)
```

#### Interrupt Handling Lifecycle [Silberschatz 10e, §1.5.2]
1. **Generation** — IRQ from device or trap instruction
2. **Processor Response** — Halts current thread at instruction boundary
3. **State Preservation** — Saves PC, PSW, registers to stack
4. **Dispatching** — Vectored (via Interrupt Vector Table) or Polling
5. **Handler Execution** — ISR runs (e.g., read keyboard buffer)
6. **State Restoration** — Restore registers/PC, resume interrupted thread

> **Stallings**: "The interrupt mechanism is the key to multiprogramming." [Stallings 9e, §3.3]

---

## 1.4 System Boot Process [Silberschatz 10e, §1.5.3; Stallings 9e, §13.1]
1. **Power On / Reset** — CPU PC points to firmware (ROM/EEPROM)
2. **Bootstrap Program** — First program to execute; initializes hardware; loads kernel
3. **Kernel Initialization** — Sets up system services, interrupt vectors, starts init process
4. **Init Process** — First user process (`init` or `systemd`); waits for events (login, daemons)

---

## 1.5 Storage Hierarchy [Silberschatz 10e, §1.4; Stallings 9e, Ch. 4]

### Memory Types [Silberschatz 10e, Table 1.1]
| Level | Technology | Speed | Capacity | Volatility | Cost/Byte |
|-------|------------|-------|----------|------------|-----------|
| Registers | CPU internal | Fastest | Smallest | Volatile | Highest |
| Cache (L1/L2/L3) | SRAM | Very Fast | Small | Volatile | High |
| Main Memory (RAM) | DRAM | Fast | Medium | Volatile | Medium |
| SSD / NVRAM | Flash | Fast | Large | Non-volatile | Medium |
| Hard Disk (HDD) | Magnetic | Slow | Very Large | Non-volatile | Low |
| Tape / Optical | Magnetic/Optical | Slowest | Huge | Non-volatile | Lowest |

### Caching Principle [Silberschatz 10e, §1.4.2]
- Copy data from slower → faster storage temporarily
- **Cache Hit** → read from fast cache
- **Cache Miss** → fetch from slow storage, populate cache
- Replacement policies: LRU, FIFO, etc.

> **Silberschatz**: "Caching is one of the most important principles of computer systems." [Silberschatz 10e, §1.4.2]

---

## 1.6 I/O Structure [Silberschatz 10e, §1.7; Stallings 9e, Ch. 7]

### DMA (Direct Memory Access) [Silberschatz 10e, §1.7.3]
- **Problem**: Interrupt per byte wastes CPU cycles for high-speed devices
- **Solution**: DMA controller transfers blocks directly between device buffer ↔ memory
- Only **one interrupt per block** instead of per byte
- CPU executes user code concurrently during transfer

### I/O Modes [Silberschatz 10e, §1.7.4]
| Mode | Behavior |
|------|----------|
| **Synchronous (Blocking)** | CPU waits for I/O completion; one request at a time |
| **Asynchronous (Non-blocking)** | CPU continues immediately; checks completion later |

---

## 1.7 Key Takeaways
- OS = Resource Allocator + Control Program [Silberschatz 10e, §1.2.1]
- Kernel = the one program running at all times [Silberschatz 10e, §1.2.1]
- Interrupts = OS's nervous system [Silberschatz 10e, §1.5]
- Storage hierarchy trades speed vs capacity vs cost [Silberschatz 10e, §1.4]
- DMA offloads bulk data movement from CPU [Silberschatz 10e, §1.7.3]

---

**Further Reading**: [Silberschatz 10e, Ch. 1-2] • [Stallings 9e, Ch. 1-2] • [Stevens & Rago 3e, Ch. 1]

# Chapter 2: Computer System Architecture

**Textbook References**: [Silberschatz 10e, Ch. 1-2] • [Stallings 9e, Ch. 2, 15] • [Stevens & Rago 3e, Ch. 2]

---

## 2.1 Processor Architectures [Silberschatz 10e, §1.2.2]

### Single Processor Systems [Silberschatz 10e, §1.2.2]
- One general-purpose CPU
- Most systems also contain **special-purpose processors** [Silberschatz 10e, §1.2.2]:
  - Device controllers (disk, keyboard, GPU)
  - Run limited instruction sets, dedicated functions
  - Offload main CPU (e.g., disk controller handles scheduling)

---

## 2.2 Multiprocessor Systems [Silberschatz 10e, §2.1; Stallings 9e, §15.1]

### Characteristics [Silberschatz 10e, §2.1]
- Two or more processors in close communication
- Share: system bus, clock, memory, peripheral devices

### Advantages [Silberschatz 10e, §2.1.1]
| Advantage | Description |
|-----------|-------------|
| **Increased Throughput** | More work in less time (not linear N× due to sync overhead) |
| **Economy of Scale** | Share peripherals, storage, power — cheaper than N single-CPU systems |
| **Fault Tolerance** | Failure of one CPU ≠ system halt; graceful degradation |

> **Silberschatz**: "Multiprocessor systems have three main advantages: increased throughput, economy of scale, and increased reliability." [Silberschatz 10e, §2.1.1]

---

## 2.3 Multiprocessor Types [Silberschatz 10e, §2.1.2]

### Asymmetric Multiprocessing (AMP) [Silberschatz 10e, §2.1.2]
- **Master-Worker** relationship
- Master: controls system, schedules, allocates work
- Workers: execute assigned tasks
- Simple but master becomes bottleneck

### Symmetric Multiprocessing (SMP) — *Modern Standard* [Silberschatz 10e, §2.1.2; Stallings 9e, §15.2]
- All processors are **peers** — no master-slave
- Each runs kernel + user code
- Each has private registers + cache; share physical memory
- Used by: Linux, Windows, macOS, Android, iOS

```
SMP Architecture [Silberschatz 10e, Fig. 2.1]:
  CPU 0          CPU 1          CPU 2
  [Regs] [Cache] [Regs] [Cache] [Regs] [Cache]
     │             │             │
     └─────────────┼─────────────┘
                   ▼
            System Bus
                   │
                   ▼
           Shared Memory
```

> **Silberschatz Fig. 2.1**: "Symmetric multiprocessing architecture" [Silberschatz 10e, Fig. 2.1]

---

## 2.4 Multicore Design [Silberschatz 10e, §2.2; Stallings 9e, §15.3]
- Multiple computing cores on **single chip** [Silberschatz 10e, §2.2]
- Each core = independent physical CPU to OS
- **Benefits**: Faster on-chip communication, less power/heat than multi-chip

```
Dual-Core Chip [Silberschatz 10e, Fig. 2.2]:
  ┌─────────────────────────────────┐
  │         PROCESSOR CHIP          │
  │  ┌──────────┐  ┌──────────┐     │
  │  │  CORE 0  │  │  CORE 1  │     │
  │  │ [Regs]   │  │ [Regs]   │     │
  │  │ [L1]     │  │ [L1]     │     │
  │  └────┬─────┘  └────┬─────┘     │
  │       │             │           │
  │       └──────┬──────┘           │
  │              ▼                  │
  │       [Shared L2/L3 Cache]      │
  └──────────────┬──────────────────┘
                 │
            Main Memory
```

> **Silberschatz Fig. 2.2**: "Dual-core design" [Silberschatz 10e, Fig. 2.2]

---

## 2.5 Advanced Architectures [Silberschatz 10e, §2.3; Stallings 9e, §15.4]

### Blade Servers [Silberschatz 10e, §2.3.1]
- High-density: multiple processor/I/O/network boards in one chassis
- Each blade boots independently, runs own OS
- Some blades are themselves multiprocessors

### Clustered Systems [Silberschatz 10e, §2.3.2; Stallings 9e, §15.5]
- Multiple independent computers (nodes) linked via high-speed interconnect
- Share storage via **SAN (Storage Area Network)** [Silberschatz 10e, §2.3.2]

| Clustering Type | Behavior |
|-----------------|----------|
| **Asymmetric** | Hot-standby monitors active; takes over on failure |
| **Symmetric** | All nodes actively run apps, monitor each other |
| **HPC** | Parallel computing via MPI/OpenMP |

- **DLM (Distributed Lock Manager)** — prevents conflicting access to shared SAN data [Silberschatz 10e, §2.3.2]

### NUMA (Non-Uniform Memory Access) [Silberschatz 10e, §2.3.3; Stallings 9e, §15.4]
- Memory access latency varies by CPU-memory distance
- Scheduler must consider memory locality

> **Silberschatz**: "In a NUMA system, the time to access a memory location depends on the location of the memory relative to the processor." [Silberschatz 10e, §2.3.3]

### Heterogeneous Multiprocessing (big.LITTLE) [Silberschatz 10e, §2.3.4]
- Cores with different performance/energy profiles
- Scheduler migrates tasks based on workload

---

## 2.6 Key Takeaways
- **SMP** = peer CPUs sharing memory; standard for modern OS [Silberschatz 10e, §2.1.2]
- **Multicore** = multiple cores on one die; each appears as CPU to OS [Silberschatz 10e, §2.2]
- **Clusters** = independent nodes + shared SAN; for HA and HPC [Silberschatz 10e, §2.3.2]
- **NUMA/big.LITTLE** = modern complexities OS scheduler must handle [Silberschatz 10e, §2.3.3-4]

---

**Further Reading**: [Silberschatz 10e, Ch. 1-2] • [Stallings 9e, Ch. 2, 15] • [Stevens & Rago 3e, Ch. 2]

# Chapter 3: Process Management

**Textbook References**: [Silberschatz 10e, Ch. 3] • [Stallings 9e, Ch. 3-4] • [Stevens & Rago 3e, Ch. 3, 7-8]

---

## 3.1 Process Concept [Silberschatz 10e, §3.1]

### Program vs Process [Silberschatz 10e, §3.1.1]
| Aspect | Program | Process |
|--------|---------|---------|
| Nature | Passive (file on disk) | Active (in execution) |
| Context | None | PC, registers, memory space, stack |
| Instances | One file | Multiple processes from same program |

> **Silberschatz**: "A program is a passive entity, such as a file containing a list of instructions stored on disk. A process is a program in execution." [Silberschatz 10e, §3.1.1]

### Process Memory Layout (32-bit) [Silberschatz 10e, Fig. 3.1; Stevens & Rago 3e, Fig. 7.6]
```
High Address (0xFFFFFFFF)
├── Command-line args & Environment (argc, argv, envp)
├── STACK (grows ↓: frames, locals, params, return addresses)
│       ↑
│       │   (free space)
│       ↓
├── HEAP (grows ↑: malloc/free)
├── BSS (uninitialized globals/statics → zeroed)
├── DATA (initialized globals/statics)
└── TEXT (code, read-only)
Low Address (0x00000000)
```

> **Silberschatz Fig. 3.1**: "Memory layout of a process" [Silberschatz 10e, Fig. 3.1]

### C Mapping Example [Stevens & Rago 3e, §7.6]
```c
int x;              // → BSS
int y = 15;         // → DATA

int main(int argc, char *argv[]) {  // args in high memory
    int *values;    // → STACK (pointer)
    int i;          // → STACK
    values = malloc(5 * sizeof(int)); // → HEAP
    for (i = 0; i < 5; i++) values[i] = i;  // → TEXT executes
    return 0;
}
```

## 3.2 Process State Model (5-State) [Silberschatz 10e, §3.2; Stallings 9e, §3.3]

```
                    [ NEW ]
                       │
                    admitted
                       ▼
        +────────> [ READY ] <─────────+
        │           │                   │
        │  dispatch │                   │
        │           ▼                   │
        │    [ RUNNING ] ──────────────+
        │        │        interrupt
        │        │
        │        │ I/O wait
        │        ▼
        │    [ WAITING ]
        │        │
        +────────┘
         I/O complete

   [ RUNNING ] ─────────> [ TERMINATED ]
              exit
```

| State | Meaning | [Silberschatz 10e, §3.2] |
|-------|---------|--------------------------|
| **New** | Being created | |
| **Ready** | In memory, waiting for CPU | |
| **Running** | Executing on CPU | |
| **Waiting** | Blocked on I/O/event | |
| **Terminated** | Finished, awaiting cleanup | |

> **Silberschatz Fig. 3.2**: "Diagram of process state" [Silberschatz 10e, Fig. 3.2]

## 3.3 Process Control Block (PCB / `task_struct`) [Silberschatz 10e, §3.3; Stevens & Rago 3e, §3.3]

**Kernel representation of each process**

| PCB Field | Description | [Silberschatz 10e, §3.3] |
|-----------|-------------|--------------------------|
| Process State | Ready, Running, Waiting... | |
| Process ID (PID) | Unique identifier | |
| Program Counter | Next instruction address | |
| CPU Registers | Accumulator, index, stack pointer | |
| Scheduling Info | Priority, queue pointers | |
| Memory Management | Page tables, base/limit | |
| Accounting | CPU time used, time limits | |
| I/O Status | Allocated devices, open files | |

**Linux `task_struct`**: `pid`, `state`, `mm` (memory), `files` (fd table), `parent`, `children` [Stevens & Rago 3e, §3.3]

> **Silberschatz**: "Each process is represented in the operating system by a process control block (PCB)." [Silberschatz 10e, §3.3]

---

## 3.4 Process Creation: `fork()` + `exec()` [Silberschatz 10e, §3.4; Stevens & Rago 3e, Ch. 8]

### The Unix Way
```c
pid = fork();  // Clone current process!
if (pid == 0) {
    // CHILD: Different program entirely
    exec("/bin/ls", "ls", NULL);  // Replaces memory with new program
} else {
    // PARENT: Continues original program
    wait(NULL);  // Wait for child to finish
}
```

> **Stevens & Rago**: "The fork() function is the only way a new process is created by an existing process." [Stevens & Rago 3e, §8.3]

### Why This Design?
- `fork()` copies everything (with **Copy-on-Write** optimization) [Silberschatz 10e, §3.4.1]
- `exec()` loads new program [Silberschatz 10e, §3.4.2]
- Separation allows: setup pipes, change directories, drop privileges *before* loading new program

### `fork()` Semantics [Stevens & Rago 3e, §8.3]
| Context | Return |
|---------|--------|
| **Child** | 0 |
| **Parent** | Child's PID (>0) |
| **Error** | -1 |

**COW**: Parent and child share physical pages read-only until one writes → then page is duplicated [Silberschatz 10e, §3.4.1].

---

## 3.5 Process Termination [Silberschatz 10e, §3.5; Stevens & Rago 3e, §8.5]

### Normal (5 ways) [Stevens & Rago 3e, §8.5]
1. `return` from `main()`
2. `exit()` — flushes buffers, runs `atexit` handlers
3. `_exit()` / `_Exit()` — direct kernel call, no cleanup
4. Last thread returns from start routine
5. `pthread_exit()` from last thread

### Abnormal (3 ways) [Stevens & Rago 3e, §8.5]
1. `abort()` → `SIGABRT`
2. Signals: `SIGKILL`, `SIGSEGV`, `SIGFPE`
3. Last thread responds to cancellation

### Zombie vs Orphan [Silberschatz 10e, §3.5; Stevens & Rago 3e, §8.6]
| | **Zombie** | **Orphan** |
|---|------------|------------|
| **Cause** | Child exited, parent hasn't `wait()` | Parent exited before child |
| **State** | Dead but PID+status in process table | Alive, no parent |
| **Resolution** | Parent calls `wait()` → reaped | Re-parented to `init`/`systemd` (PID 1) |

> **Stevens & Rago**: "A process that has terminated, but whose parent has not yet waited for it, is called a zombie." [Stevens & Rago 3e, §8.6]

---

## 3.6 Process Scheduling & Queues [Silberschatz 10e, §3.6]

### Three Queues [Silberschatz 10e, §3.6.1]
| Queue | Contents |
|-------|----------|
| **Job Queue** | All processes in system |
| **Ready Queue** | In memory, ready to execute |
| **Device/Waiting Queues** | Blocked on specific I/O/event |

### Scheduler Types [Silberschatz 10e, §3.6.2]
| Scheduler | Frequency | Role |
|-----------|-----------|------|
| **Short-term (CPU)** | Milliseconds | Pick next ready process → dispatch |
| **Long-term (Job)** | Seconds/minutes | Admit processes from disk to memory (controls **degree of multiprogramming**) |
| **Medium-term (Swapper)** | As needed | Swap out to disk (free memory) → swap in later |

### Process Types [Silberschatz 10e, §5.1.1]
| Type | Behavior | CPU Bursts |
|------|----------|------------|
| **I/O-Bound** | More I/O than compute | Many, short |
| **CPU-Bound** | More compute than I/O | Few, long |

**Scheduler goal**: Balance mix for good utilization + responsiveness

---

## 3.6 Context Switching [Silberschatz 10e, §3.7; Stallings 9e, §3.4]

**Mechanism**: Save current process state to PCB, load next process state from PCB

```
P0 Running → Interrupt → Save PCB0 → Load PCB1 → P1 Running
             ↑                               │
             └── Interrupt → Save PCB1 → Load PCB0 ───┘
```

### Overhead (Pure System Cost) [Silberschatz 10e, §3.7]
- Save/restore: GPRs, PC, SP, FP registers
- Flush/invalidate **TLB**
- Switch address space (page table base register)
- **Factors**: Hardware register sets, PCB size, OS complexity

> **Silberschatz**: "Context-switch time is pure overhead, because the system does no useful work while switching." [Silberschatz 10e, §3.7]

---

## 3.8 Key Takeaways
- **Process** = active entity with memory layout (TEXT, DATA, BSS, HEAP, STACK) [Silberschatz 10e, §3.1]
- **5-State Model**: New → Ready ↔ Running → Waiting → Terminated [Silberschatz 10e, §3.2]
- **PCB** = kernel's process representation (Linux: `task_struct`) [Silberschatz 10e, §3.3]
- **fork()/exec()** = standard creation pattern [Silberschatz 10e, §3.4]
- **Zombie** = dead, un-waited; **Orphan** = re-parented to init [Silberschatz 10e, §3.5]
- **Three schedulers**: Short-term (CPU), Long-term (admission), Medium-term (swapping) [Silberschatz 10e, §3.6]
- **Context switch** = save/restore PCB + TLB flush + address space switch [Silberschatz 10e, §3.7]

---

**Further Reading**: [Silberschatz 10e, Ch. 3] • [Stallings 9e, Ch. 3-4] • [Stevens & Rago 3e, Ch. 3, 7-8]

# Chapter 4: CPU Scheduling

**Textbook References**: [Silberschatz 10e, Ch. 5] • [Stallings 9e, Ch. 9] • [Stevens & Rago 3e, Ch. 9]

---

## 4.1 Basic Concepts [Silberschatz 10e, §5.1]

### Motivation [Silberschatz 10e, §5.1.1]
- Single CPU core → only one process executes at a time
- Others wait in **ready queue**
- **Multiprogramming objective**: Keep CPU busy at all times
- When process waits (I/O), scheduler switches to another ready process

### CPU-I/O Burst Cycle [Silberschatz 10e, Fig. 5.1]
```
CPU burst → I/O burst → CPU burst → I/O burst → ...
```
- CPU burst distribution drives scheduling algorithm design

> **Silberschatz Fig. 5.1**: "The CPU-I/O burst cycle" [Silberschatz 10e, Fig. 5.1]

---

## 4.2 Scheduler & Dispatcher [Silberschatz 10e, §5.2]

| Component | Role | [Silberschatz 10e, §5.2] |
|-----------|------|--------------------------|
| **Short-term scheduler** | Picks next process from ready queue | |
| **Dispatcher** | Context switch, mode change, jump to user code | |
| **Dispatch latency** | Time to stop one process, start another | |

---

## 4.3 Preemptive vs Non-Preemptive Scheduling [Silberschatz 10e, §5.3]

### Four Decision Points [Silberschatz 10e, §5.3.1]
| # | Transition | Non-Preemptive | Preemptive |
|---|------------|----------------|------------|
| 1 | Running → Waiting (I/O) | ✅ | ✅ |
| 2 | Running → Ready (interrupt) | ❌ | ✅ |
| 3 | Waiting → Ready (I/O done) | ❌ | ✅ |
| 4 | Running → Terminated | ✅ | ✅ |

| Type | Description | [Silberschatz 10e, §5.3] |
|------|-------------|--------------------------|
| **Non-Preemptive** | Process keeps CPU until it voluntarily releases (I/O or terminate) | |
| **Preemptive** | OS can forcibly preempt on timer interrupt or higher-priority arrival | |

**Preemptive challenges**: Race conditions on shared data; need kernel synchronization [Silberschatz 10e, §5.3.2]

---

## 4.4 Scheduling Criteria (Metrics) [Silberschatz 10e, §5.4]

| Metric | Goal | Description | [Silberschatz 10e, §5.4] |
|--------|------|-------------|--------------------------|
| **CPU Utilization** | Maximize | % time CPU busy (40-90%) | |
| **Throughput** | Maximize | Processes completed per unit time | |
| **Turnaround Time** | Minimize | Submit → complete (wait + exec + I/O) | |
| **Waiting Time** | Minimize | Time in ready queue | |
| **Response Time** | Minimize | Submit → first response (interactive) | |

---

## 4.5 Scheduling Algorithms [Silberschatz 10e, §5.5]

### 1. First-Come, First-Served (FCFS) [Silberschatz 10e, §5.5.1]
- **Algorithm**: FIFO ready queue, **non-preemptive**
- **Simple** but suffers **Convoy Effect**

#### Example 1: P1(24), P2(3), P3(3) at t=0
```
Gantt: | P1 (24) | P2 (3) | P3 (3) |
       0        24       27       30
Wait: P1=0, P2=24, P3=27 → Avg = 17.0 ms
```

#### Example 2: P2(3), P3(3), P1(24) at t=0
```
Gantt: | P2 (3) | P3 (3) | P1 (24) |
       0        3        6        30
Wait: P2=0, P3=3, P1=6 → Avg = 3.0 ms
```

**Convoy Effect** [Silberschatz 10e, §5.5.1]: Short I/O-bound processes stuck behind long CPU-bound process → poor utilization

---

### 2. Shortest-Job-First (SJF) — Non-Preemptive [Silberschatz 10e, §5.5.2]
- **Algorithm**: Pick process with **smallest next CPU burst**
- **Tie-breaker**: FCFS
- **Provably optimal** for minimum average waiting time (stationary processes) [Silberschatz 10e, §5.5.2]

#### Example: All arrive at t=0
| Process | Burst |
|---------|-------|
| P1 | 6 |
| P2 | 8 |
| P3 | 7 |
| P4 | 3 |

**Order**: P4(3) → P1(6) → P3(7) → P2(8)
```
Gantt: | P4 | P1 | P3 | P2 |
       0    3    9   16   24
Wait: P4=0, P1=3, P3=9, P2=16 → Avg = 7.0 ms
```
vs FCFS (P1,P2,P3,P4): Avg = 10.25 ms

> **Silberschatz**: "SJF is provably optimal, in that it gives the minimum average waiting time for a given set of processes." [Silberschatz 10e, §5.5.2]

---

### 3. Shortest-Remaining-Time-First (SRTF) — Preemptive SJF [Silberschatz 10e, §5.5.3]
- Preempt if new arrival has **shorter remaining burst** than current

#### Example with Arrival Times
| Process | Arrival | Burst |
|---------|---------|-------|
| P1 | 0 | 8 |
| P2 | 1 | 4 |
| P3 | 2 | 9 |
| P4 | 3 | 5 |

**Timeline**:
```
t=0: P1 starts (rem=8)
t=1: P2 arrives (4 < 7) → preempt P1, run P2
t=2: P3 arrives (9 > 3) → P2 continues
t=3: P4 arrives (5 > 2) → P2 continues
t=5: P2 done. Ready: P1(7), P3(9), P4(5) → run P4
t=10: P4 done. Ready: P1(7), P3(9) → run P1
t=17: P1 done. Run P3
t=26: P3 done.

Gantt: | P1 | P2 | P4 | P1 | P3 |
       0    1    5   10   17   26

Wait: P1=9, P2=0, P3=15, P4=2 → Avg = 6.5 ms
```

---

### 4. Priority Scheduling [Silberschatz 10e, §5.5.4]
- Each process has **integer priority**
- CPU → highest priority process
- **Conventions**: Smaller integer = higher priority (Silberschatz) OR larger = higher [Silberschatz 10e, §5.5.4]
- **Preemptive** or **Non-preemptive**
- **SJF = special case** where priority = 1 / predicted burst

#### Starvation Problem [Silberschatz 10e, §5.5.4]
- Low-priority process waits indefinitely if high-priority stream continues
- **Solution: Aging** — gradually increase priority of waiting processes [Silberschatz 10e, §5.5.4]

#### Example: Non-Preemptive (Smaller = Higher)
| Process | Burst | Priority |
|---------|-------|----------|
| P1 | 10 | 3 |
| P2 | 1 | 1 (Highest) |
| P3 | 2 | 4 |
| P4 | 1 | 5 (Lowest) |
| P5 | 5 | 2 |

**Order**: P2 → P5 → P1 → P3 → P4
```
Avg Wait = 8.2 ms
```

#### Example: Preemptive (Larger = Higher)
| Process | Arrival | Burst | Priority |
|---------|---------|-------|----------|
| P1 | 0 | 4 | 2 |
| P2 | 1 | 3 | 3 |
| P3 | 2 | 1 | 4 |
| P4 | 3 | 5 | 5 (Highest) |
| P5 | 4 | 2 | 5 (Highest) |

```
Avg Wait = 4.6 ms
```

---

### 5. Round-Robin (RR) — *Designed for Time-Sharing* [Silberschatz 10e, §5.5.5]
- **Preemptive**, based on FCFS
- **Time Quantum (q)**: 10-100ms typical
- Ready queue = circular FIFO
- Process runs for ≤ q; if not done, preempted → appended to tail

#### Example: q=4, P1(24), P2(3), P3(3) at t=0
```
Gantt: | P1 | P2 | P3 | P1 | P1 | P1 | P1 | P1 |
       0    4    7   10   14   18   22   26   30

Wait: P1=6, P2=4, P3=7 → Avg = 5.66 ms
```

### RR Performance Analysis [Silberschatz 10e, §5.5.5]
| Quantum Size | Behavior |
|--------------|----------|
| **q → ∞** | Degenerates to **FCFS** |
| **q → 0** | Approaches **processor sharing** (each gets 1/n speed) but **context-switch overhead dominates** |

**Rule of Thumb** [Silberschatz 10e, §5.5.5]: ~80% of CPU bursts should complete within one quantum

---

### 6. Multilevel Queue (MLQ) [Silberschatz 10e, §5.5.6]
- Processes permanently assigned to queues (foreground/background)
- Each queue has own scheduling (RR for foreground, FCFS for background)
- **Inter-queue scheduling**:
  - Fixed-priority (higher queues must empty first) → starvation risk
  - Time-sliced (e.g., 80% foreground, 20% background)

### Multilevel Feedback Queue (MLFQ) — *Self-Tuning* [Silberschatz 10e, §5.5.7]
- **Dynamic migration** between queues based on behavior
- Standard 3-queue example:
  ```
  NEW → Q0 (RR, q=8) → Q1 (RR, q=16) → Q2 (FCFS)
  ```
- **Demotion**: Use full quantum → move down
- **Promotion (Aging)**: Wait too long → move up
- **Preemption**: Higher queue arrival preempts lower

> **Silberschatz**: "The multilevel feedback queue is the most general scheduling algorithm, but it is also the most complex to implement." [Silberschatz 10e, §5.5.7]

---

## 4.6 Thread Scheduling [Silberschatz 10e, §5.6]
- **PCS (Process-Contention Scope)**: User-level scheduling (M:1, M:N) [Silberschatz 10e, §5.6.1]
- **SCS (System-Contention Scope)**: Kernel schedules directly (1:1 — Linux default) [Silberschatz 10e, §5.6.2]

---

## 4.7 Summary Table [Silberschatz 10e, Table 5.2]

| Algorithm | Preemptive? | Best For | Drawback |
|-----------|-------------|----------|----------|
| FCFS | No | Simple batch | Convoy effect |
| SJF | No | Minimum wait | Needs burst prediction |
| SRTF | Yes | Responsive batch | More context switches |
| Priority | Both | Importance-based | Starvation (fix: aging) |
| RR | Yes | Time-sharing | Quantum tuning critical |
| MLFQ | Yes | General purpose | Complex tuning |

---

## 4.8 Key Formulas [Silberschatz 10e, §5.4]

| Metric | Formula |
|--------|---------|
| **Turnaround Time** | Completion - Arrival |
| **Waiting Time** | Turnaround - Burst = Completion - Arrival - Burst |
| **Response Time** | First Start - Arrival |
| **Avg Waiting** | Σ Wait_i / n |
| **RR Max Wait Bound** | (n - 1) × q |

---

## Key Takeaways
- **FCFS**: Simple but convoy effect [Silberschatz 10e, §5.5.1]
- **SJF/SRTF**: Optimal for wait time but need burst prediction [Silberschatz 10e, §5.5.2-3]
- **Priority**: Flexible but starvation → fix with aging [Silberschatz 10e, §5.5.4]
- **RR**: Fair, predictable; quantum tuning critical (80% rule) [Silberschatz 10e, §5.5.5]
- **MLFQ**: Self-tuning; adapts to actual behavior [Silberschatz 10e, §5.5.7]
- **Real systems**: Use MLFQ variants (Linux CFS, Windows, macOS) [Silberschatz 10e, §5.5.7]

---

**Further Reading**: [Silberschatz 10e, Ch. 5] • [Stallings 9e, Ch. 9] • [Stevens & Rago 3e, Ch. 9]

# Chapter 10: Shell Programming & Cron Scheduling

## 10.1 Linux Shell

### Definition & Role
```
[ User / Terminal ] ↔ [ Shell Interpreter ] ↔ [ OS Kernel ] ↔ [ Hardware ]

- **Command-line interpreter (CLI)** — reads commands, parses, resolves executables, requests kernel to spawn processes

- Tokenizes into: command name, flags/options, target arguments
- **Path resolution**:

## 10.5 Cron Scheduling Daemon

### Overview

### Crontab Syntax (5 Fields)

```
