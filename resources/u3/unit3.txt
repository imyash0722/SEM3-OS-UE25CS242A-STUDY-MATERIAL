Logical vs. Physical Address Space
OPERATING SYSTEMS
●The concept of a logical address space that is bound to a separate 
physical address space is central to proper memory management
●Logical address – generated by the CPU; also referred to as virtual 
address
●Physical address – address seen by the memory unit
●Logical and physical addresses are the same in compile-time and load-
time address-binding schemes; logical (virtual) and physical addresses 
differ in execution-time address-binding scheme
●Logical address space is the set of all logical addresses generated by a 
program
●Physical address space is the set of all physical addresses generated 
by a program

Memory-Mapped Files (mmap)
OPERATING SYSTEMS
Mapping file contents directly into the process virtual address space.Access disk files via memory pointers (ptr[i]) instead of 
standard I/O system calls.Eliminate data duplication between kernel buffers and user space.
How It Works:
Address Translation: OS allocates a virtual address range to the file without loading it into physical RAM.
OS Support & Page Faults: Reading an address triggers a hardware page fault; the OS then pages the disk content into Main 
Memory.
Dynamic Shared Libraries: Uses the same mechanism as shared libraries to allow multiple processes to share memory safely.
Two Core Modes
Shared Mapping (MAP_SHARED): Writes modify the actual file on disk and are instantly visible to other processes.
Private Mapping (MAP_PRIVATE): Utilizes Copy-on-Write (CoW); modifications stay in memory and never change the disk file.
Advantages
High Performance: Bypasses overhead from read() and write() system calls.
Zero-Copy I/O: Transfers data directly from disk cache to user space.
Efficient IPC: Enables lightning-fast Inter-Process Communication via shared physical pages.
UNIVERSITY

--- [Slide / Page 23] ---
1. First access:A demand-paging fault occurs; a page-sized chunk of the file is read from disk into a 
physical page.
2. Subsequent access:Reads and writes to the file are handled as ordinary memory accesses — no 
read()/write() system call overhead.
3. Deferred write-back:Modified pages aren't written to disk immediately; under memory pressure 
they're paged to swap space instead of being lost.
4. On close:All memory-mapped data is written back to secondary storage and unmapped from the 
process's virtual memory.
Solaris Example:
•mmap(): File is mapped directly into the process's address space.
•open() / read() / write(): File is still memory-mapped — but into kernel address space.
•Net effect: All file I/O goes through the efficient memory subsystem, avoiding traditional system-
call overhead.

Memory-Mapped Files: Advantages and Sharing Memory
OPERATING SYSTEMS
•
Concurrent access, copy-on-write, and shared memory
•
Concurrent Sharing
Multiple processes can map the same file at once. Each process's 
virtual memory map points to the same physical page — the page 
holding the disk block — so writes by one process are immediately 
visible to all others.
•
Copy-on-Write
Mapping calls can support copy-on-write: processes share a file 
read-only, but any process that modifies data gets its own private 
copy of just that data.
•
Shared Memory via mmap (diagram box)
•Process A → Mapped File (shared region)
•Process B → Mapped File (shared region)
•Each communicating process memory-maps the same file (or POSIX shared-memory object) into its 
address space — the mapping itself becomes the shared-memory region for IPC.
•
Coordinating Access
Since the memory is shared, processes typically use a mutual-exclusion mechanism to coordinate 
access to the shared data.

Swapping
OPERATING SYSTEMS
●A process can be swapped temporarily out of memory to a backing store, and then brought back 
into memory for continued execution
●Total physical memory space of processes can exceed physical memory
●Backing store – fast disk large enough to accommodate copies of all memory images for all users; 
must provide direct access to these memory images
●Roll out, roll in – swapping variant used for priority-based scheduling algorithms; lower-priority 
process is swapped out so higher-priority process can be loaded and executed
●Major part of swap time is transfer time; total transfer time is directly proportional to the amount 
of memory swapped
●System maintains a ready queue of ready-to-run processes which have memory images on disk
UNIVERSITY

Swapping (Cont.)
OPERATING SYSTEMS
●Does the swapped out process need to swap back in to same physical addresses?
●Depends on address binding method
●Plus consider pending I/O to / from process memory space
●Modified versions of swapping are found on many systems (i.e., UNIX, Linux, and Windows)
●Swapping normally disabled
●Started if more than threshold amount of memory allocated
●Disabled again once memory demand reduced below threshold

Memory Protection
OPERATING SYSTEMS
●Every address generated by a CPU is checked against these registers, so 
possible to protect both the operating system and the other users’ programs 
and data from being modified by this running process . 
●The relocation-register scheme provides an effective way to allow the

Multiple-partition allocation
OPERATING SYSTEMS
●Multiple-partition allocation
●Divide memory into several fixed-size partitions.
●Each partition may contain exactly one process
●Degree of multiprogramming is bounded by number of partitions.

●Variable-partition sizes for efficiency (sized to a given process’ needs)
●This scheme keeps a table indicating which parts of memory are 
available/occupied
●Hole – block of available memory; holes of various size are scattered 
throughout memory

Effective Access Time
OPERATING SYSTEMS
▪Hit ratio – percentage of times that a page number is found in the  TLB
▪An 80% hit ratio means that we find the desired  page number  in the TLB 80% of the time.
▪Suppose that 10 nanoseconds to access memory.  
• If we find the desired page in TLB then a mapped-memory access take 10 ns
• Otherwise we need two memory access so it is 20 ns i.e. if we fail to find the page number in 
the TLB then we must first access memory for the page table and frame number (10 ns) and then 
access the desired byte in memory (10 nanoseconds), for a total of 20 ns (assuming that a page 
table lookup takes only one memory access).
▪Effective Access Time (EAT)
               EAT = 0.80 x 10 + 0.20 x 20 = 12  nanoseconds
       implying 20% slowdown in access time
▪Consider a more realistic hit ratio of 99%, 
     EAT = 0.99 x 10 + 0.01 x 20 = 10.1ns
      implying  only 1% slowdown in access time.

Translation Look-Aside Buffer 
OPERATING SYSTEMS
How TLB is different from CPU Cache 
▪TLB is about ‘speeding up address translation for Virtual/logical memory’ so 
that page-table needn’t to be accessed for every address.
▪ CPU Cache is about ‘speeding up main memory access latency’ so that RAM 
isn’t accessed always by CPU.
▪ TLB operation comes at the time of address translation by MMU while CPU 
cache operation comes at the time of memory access by CPU.

Inverted Page Table
OPERATING SYSTEMS
• Systems that use inverted page tables have difficulty in implementing shared 
memory.
• Shared memory is usually implemented as multiple virtual addresses are 
mapped to one physical address. 
• There is only one virtual page entry for every physical page
• One physical page cannot have two (or more) shared virtual addresses.
• A simple technique for addressing this issue is to allow the page table to 
contain only one mapping of a virtual address to the shared physical address.
• references to virtual addresses that are not mapped result in page faults

Major vs Minor page faults

Copy-on-Write
OPERATING SYSTEMS
●Copy-on-Write (COW) allows both parent and child processes to initially share the same 
pages in memory
●If either process modifies a shared page, only then is the page copied
●COW allows more efficient process creation as only modified pages are copied
●In general, free pages are allocated from a pool of zero-fill-on-demand pages
●Pool should always have free frames for fast demand page execution
4 Don’t want to have to free a frame as well as other processing on page fault
•
Hardware Enforcement: The OS marks the page table entries for both processes as Read-
Only.
•
The Trap: If either process attempts to modify the data, the MMU triggers a hardware 
protection fault. The OS intercepts this trap, realizes it's a COW page, allocates a new 
physical frame, copies the data, updates the page table to Read/Write, and restarts the 
instruction.

Linux Angle

Allocation of Frames
OPERATING SYSTEMS
●How do we allocate the fixed amount of free memory among the various processes? 
Example:
●Consider a single-user system with 128 KB of memory composed of pages 1 KB in size. Therefore, 
this system has 128 frames.
●The operating system may take 35 KB, leaving 93 frames for the user process.
●When a user process started execution, under pure demand paging, it would generate a sequence 
of page faults.
●The first 93 page faults would all get free frames from the free-frame list. 
●When the free-frame list is exhausted, a page-replacement algorithm would be used.
●When the process is terminated, the 93 frames would once again be placed on the free-frame list
UNIVERSITY

--- [Slide / Page 14] ---
Allocation of Frames
OPERATING SYSTEMS
Minimum number of frames:
●One reason for allocating at least a minimum number of frames involves performance. 
●As the number of frames allocated to each process decreases, the page-fault rate increases, 
slowing process execution
●When a page fault occurs before an executing instruction is complete, the instruction must be 
restarted. Consequently, we must have enough frames to hold all the different pages that any 
single instruction can reference
●The minimum number of frames is defined by the computer architecture.
●The maximum number is defined by the amount of available physical memory. 
●In between, we are still left with significant choice in frame allocation
UNIVERSITY

Frame Allocation Algorithms
OPERATING SYSTEMS
Equal allocation:
●The easiest way to split m frames among n processes is to give everyone an equal share,      
m/n frames (ignoring frames needed by the operating system)
      Example:
●If there are 93 frames and 5 processes, each process will get 18 frames. 
●The three leftover frames can be used as a free-frame buffer pool. 
UNIVERSITY

--- [Slide / Page 16] ---
Frame Allocation Algorithms
OPERATING SYSTEMS
Proportional allocation:
●Allocate available memory to each process according to its size
●Let the size of the virtual memory for process pi be si and define S = ∑ si 
●If the total number of available frames is m, allocate ai frames to process pi , where ai is 
approximately ai = si / S × m
●Adjust each ai to be an integer that is greater than the minimum number of frames required by 
the instruction set, with a sum not exceeding m
●Example:  To allocate 62 frames between two processes, one of 10 pages and one of 127 pages
●10/137 × 62 ≈ 4
●127/137 × 62 ≈ 57

--- [Slide / Page 17] ---
Global versus Local Allocation
OPERATING SYSTEMS
•
Page-replacement algorithms can be classified into two broad categories: global replacement and local replacement
•
Global replacement allows a process to select a replacement frame from the set of all frames, even if that frame is 
currently allocated to some other process; that is, one process can take a frame from another. 
•
Local replacement requires that each process select from only its own set of allocated frames.
•
Example: Consider a global replacement scheme wherein high-priority processes are allowed to select frames from 
low-priority processes for replacement. 
•
A process can select a replacement from among its own frames or the frames of any lower-priority process. This 
approach allows a high-priority process to increase its frame allocation at the expense of a low-priority process
•
With a local replacement strategy, the number of frames allocated to a process does not change.
•
Global replacement generally results in greater system throughput and is therefore the more commonly used 
method.

Non-uniform Memory Access
OPERATING SYSTEMS
•
In systems with multiple CPUs, a given CPU can access some sections of main memory faster than it can 
access others. 
•
These performance differences are caused by how CPUs and memory are interconnected in the system.
•
Systems in which memory access times vary significantly are known collectively as non-uniform memory 
access (NUMA) systems, and without exception, they are slower than systems in which memory and 
CPUs are located on the same motherboard
•
Managing which page frames are stored at which locations can significantly affect performance in NUMA 
systems. If we treat memory as uniform in such a system, CPUs may wait significantly longer for memory 
access than if we modify memory allocation algorithms to take NUMA into account.

Memory locality
OPERATING SYSTEMS
Memory locality refers to the tendency of a program to access the same memory 
locations or nearby memory locations repeatedly over a short period of time. The 
principle of locality is the basis for efficient memory hierarchy design (registers, cache, 
RAM and virtual memory). Memory locality improves system performance by: 
•    Reducing memory access time. 
•    Increasing CPU cache hit rate. 
•    Decreasing cache misses. 
•    Improving virtual memory and paging efficiency. 
•    Enhancing overall execution speed. 
UNIVERSITY

--- [Slide / Page 8] ---
Types of Memory locality
OPERATING SYSTEMS
1. Temporal Locality (Locality in Time)
If a memory location is accessed, it is likely to be accessed again in the near future.
Applications:
CPU cache stores recently accessed data. 
Frequently used instructions remain in the instruction cache. 
2. Spatial Locality (Locality in Space)
If a memory location is accessed, nearby memory locations are likely to be accessed soon.
Applications:
Cache loads an entire cache block (cache line), not just one memory location. 
Sequential file reading benefits from spatial locality.

## 15.1 Background: Memory Basics

### What is Memory?
- Memory consists of a large array of bytes, each with its own address
- Execution: Fetch instruction → Decode → Fetch operands → Execute → Store results
- Memory unit sees stream of addresses; doesn't know how generated

### Program Execution Requirements
- Program must be brought from disk into memory, placed in ready queue
- Main memory and registers: only storage CPU accesses directly
- Register access: 1 CPU clock; Main memory: many cycles (stall)
- Cache between registers and main memory speeds up access (no OS control)

---

## 15.2 Address Translation & Hardware Support

### Address Binding
- **Compile time**: Absolute code; if start address changes → recompile (MS-DOS .COM)
- **Load time**: Relocatable code; final binding at load time
- **Execution time**: Process can move during execution; binding delayed until run time; needs hardware support (MMU)

### Memory-Management Unit (MMU)
- Hardware device mapping virtual → physical address at run time
- Multiple methods: will be discussed

### Logical vs Physical Address
```
Logical Address (CPU) → MMU → Physical Address (Memory)
```
- **Logical (virtual)**: Generated by CPU
- **Physical**: Seen by memory unit
- Same in compile/load-time binding; differ in execution-time binding

### Base & Limit Registers (Protection & Relocation)
```
Base register = relocation register = starting physical address
Limit register = range/size of logical address space
Legal: 0 ≤ Logical < Limit
Physical = Base + Logical
If Logical ≥ Limit → Hardware Trap (Addressing/Segmentation fault)
```
- Base/limit loaded only by OS via privileged instruction (kernel mode)
- Prevents user programs from modifying OS or other users' memory

### Dynamic Relocation (Relocation Register)
- Value in relocation register added to every user address at time sent to memory
- Example: base=14000, user address 0 → physical 14000; address 346 → 14346
- User program deals with logical addresses; never sees real physical addresses

---

## 15.3 OS Support

### Memory Allocation Strategies
| Strategy | Description |
|----------|-------------|
| **First Fit** | Allocate first hole big enough (fastest) |
| **Best Fit** | Allocate smallest hole big enough (leaves smallest leftover) |
| **Worst Fit** | Allocate largest hole (leaves largest leftover; worst utilization) |

### Memory Protection
- Valid/invalid bits in page tables
- Read/Write/Execute permission bits

### Shared Pages
- Code sharing between processes
- Copy-on-write (COW) for fork()

---

## 15.4 Dynamic Loading & Linking

### Dynamic Loading
- Routine loaded **only when called** (not at startup)
- Reduces memory footprint, faster startup

### Dynamic Linking
- Linking **postponed until execution** (shared libraries)
- Single library copy in memory shared by multiple processes
- **Shared Libraries**: `.so` (Linux), `.dll` (Windows)
- **Stub**: Small code piece locates library routine; replaces itself with routine address

### Static vs Dynamic Linking
| Aspect | Static | Dynamic |
|--------|--------|---------|
| Libraries | Embedded in executable | Loaded at runtime |
| Memory | Each program has copy | Single copy shared |
| Disk Space | Wasted (duplicate libs) | Efficient |
| Updates | Recompile needed | Auto-use new library |

---

## 15.5 Memory-Mapped Files (`mmap()`)

```c
#include <sys/mman.h>

void *mmap(void *addr, size_t len, int prot, int flags, int fd, off_t offset);
// Map file into memory — treats file I/O as memory access

munmap(void *addr, size_t len);  // Unmap
```

### Parameters
| Parameter | Description |
|-----------|-------------|
| `addr` | Hint address (NULL = kernel chooses) |
| `len` | Length of mapping |
| `prot` | Protection: `PROT_READ`, `PROT_WRITE`, `PROT_EXEC`, `PROT_NONE` |
| `flags` | `MAP_SHARED` (changes to file, visible to others) / `MAP_PRIVATE` (COW) |
| `fd` | File descriptor from `open()` |
| `offset` | Offset into file (page-aligned) |

### MAP_SHARED vs MAP_PRIVATE
| Mode | Behavior |
|------|----------|
| `MAP_SHARED` | Writes modify file on disk; visible to other processes |
| `MAP_PRIVATE` | COW; changes stay in memory, not written to file |

### mmap() Lifecycle
1. **First access**: Demand-paging fault; page-sized chunk read from disk
2. **Subsequent access**: Memory accesses — no `read()`/`write()` overhead
3. **Deferred write-back**: Modified pages paged to swap under memory pressure
4. **On close**: Data written back to disk, unmapped

### Advantages
- **High Performance**: Bypasses `read()`/`write()` overhead
- **Zero-Copy I/O**: Direct disk cache → user space
- **Random Access**: Direct address access, no sequential reads
- **Efficient for Large Files**: Demand paging loads only needed pages
- **Easy Programming**: `data[100]` accesses file location
- **Sharing**: Multiple processes map same file → share physical pages
- **IPC**: Memory-mapped shared memory for fast IPC

---

## 15.5 Key Takeaways

1. **Base/Limit** = simple relocation + protection
2. **MMU** = hardware translation unit
3. **Dynamic Loading** = load on demand
4. **Dynamic Linking** = shared libraries at runtime
5. **mmap()** = file I/O as memory access; `MAP_SHARED` vs `MAP_PRIVATE`
6. **First/Best/Worst Fit** = contiguous allocation strategies

# Topic 16 (Detailed): Swapping & Fragmentation

**Source**: Lecture 3.2 (Unit 3) + Textbook Ch. 8 (Silberschatz Ch. 8)

---

## 16.1 Swapping

### Concept
- Process swapped temporarily out of memory to backing store, then back for continued execution
- Total physical memory space of processes can exceed physical memory
- **Backing store**: Fast disk large enough for all memory images; direct access required

### Swapping Variants
| Variant | Description |
|--------|-------------|
| **Roll out, roll in** | Priority-based; lower-priority swapped out for higher-priority |
| **Standard** | Swapping disabled normally; enabled when memory > threshold |

### Swapping Details
- **Backing store**: Fast disk, direct access to memory images
- **Transfer time**: Major part of swap time; proportional to memory size
- **Ready queue**: Processes with memory images on disk

### Context Switch with Swapping
```
Example: 100MB process, 50MB/sec disk
Swap out = 100/50 = 2 sec
Swap in = 2 sec
Total context switch = 4 seconds (just swapping)
```
- 3GB process → 60 seconds swap time!
- **Optimization**: Swap only used memory via `request_memory()`/`release_memory()`

### Swapping Constraints
- **Pending I/O**: Can't swap out (I/O would go to wrong process) → double buffering
- **Standard swapping** rarely used in modern OS; modified versions common
- Swapping disabled normally; enabled when memory > threshold

---

## 16.2 Contiguous Memory Allocation

### Memory Layout
```
Low addr ──► [OS: interrupt vector, kernel] ──► [User Processes] ──► High addr
```

### Hardware Support
- **Base register**: Smallest physical address
- **Limit register**: Logical address range (address < limit)
- **MMU**: Maps logical → physical dynamically
- **Dispatcher**: Loads base/limit registers during context switch

### Memory Protection
- Every CPU address checked against base/limit
- Protects OS and other users' programs
- Allows dynamic OS size (e.g., load device drivers on demand)

---

## 16.3 Partition Allocation

### Fixed Partitions (IBM OS/360)
- Memory divided into fixed-size partitions
- One process per partition
- Degree of multiprogramming = number of partitions
- **Internal fragmentation**: allocated > requested

### Variable Partitions (Modern)
- Partitions sized to process needs
- Hole = block of available memory
- OS maintains table of allocated/free partitions
- Process allocated from sufficiently large hole
- On exit: partition freed, adjacent free holes combined

### Example Problem
```
Processes: 5=100MB, 8=400MB, 2=200MB, 9=200MB, 10=100MB
Process 5 terminates → can 11=200MB be accommodated?
```

---

## 16.4 Dynamic Storage Allocation Strategies

| Strategy | Description | Pros/Cons |
|----------|-------------|-----------|
| **First Fit** | First hole big enough | Fast; good utilization |
| **Best Fit** | Smallest hole big enough | Smallest leftover; must search all |
| **Worst Fit** | Largest hole | Largest leftover; poor utilization |

### Example
```
Partitions: 300, 600, 350, 200, 750, 125 KB
Processes: 115, 500, 358, 200, 375 KB
```

### 50% Rule (First Fit)
- N allocated blocks → ~0.5N blocks lost to fragmentation
- ~1/3 memory unusable: `(0.5N)/(N+0.5N) = 1/3`

---

## 16.5 Fragmentation

| Type | Description | Solution |
|------|-------------|----------|
| **Internal** | Allocated > requested; unused within partition | Paging (fixed frames) |
| **External** | Total free space exists but not contiguous | Paging; Compaction |

### Compaction
- Shuffle memory to create one large free block
- Requires dynamic relocation (execution-time binding)
- **Problem**: CPU overhead of moving 8GB RAM!
- **I/O issue**: Latch job during I/O; use OS buffers

---

## 16.6 Key Takeaways

1. **Swapping** = medium-term scheduler moves processes between RAM and disk
2. **External fragmentation** = free but non-contiguous; solved by paging
3. **Internal fragmentation** = allocated > requested; paging has internal frag on last page
4. **50% rule** = 0.5N blocks lost for N allocated blocks
5. **Compaction** = move processes to create large contiguous free space

---

## 16.7 Exam-Relevant MCQ Patterns

- **Q73**: Best Fit → smallest leftover hole
- **Q74**: 50% rule → 0.5N blocks lost (1/3 memory unusable)
- **Q75**: Paging eliminates external fragmentation but has internal fragmentation on last page

# Topic 17 (Detailed): Segmentation

**Source**: Lecture 3.3 (Unit 3) + Textbook Ch. 8 (Silberschatz Ch. 8)

---

## 17.1 Segmentation Basics

### Concept
- Memory-management scheme supporting **programmer's view of memory**
- Program = collection of **segments** (logical units):
  - Main program, procedure, function, method, object
  - Local/global variables, common block, stack, symbol table, arrays

### Programmer's View
```
Logical address = <segment-number s, offset d>
```
- Segment = logical unit (code, data, stack, etc.)
- Addresses: segment name + offset within segment

---

## 17.2 Segmentation Architecture

### Logical Address
```
<segment-number s, offset d>
```

### Segment Table
Each entry contains:
- **Segment base**: Starting physical address of segment
- **Segment limit**: Length of segment

### Registers
- **STBR** (Segment Table Base Register): Points to segment table in memory
- **STLR** (Segment Table Length Register): Number of segments used
  - Valid segment: `s < STLR`

---

## 17.3 Address Translation

```
Logical:  s (segment #) | d (offset)
                │
                ▼
        Segment Table[s] → Base, Limit
                │
                ├── Check: d < Limit? → if not → Trap (Segmentation Fault)
                │
                ▼
           Physical = Base + d
```

### Example
```
Segment Table:
Seg 0: Base=219, Limit=600
Seg 1: Base=2300, Limit=14
Seg 2: Base=90, Limit=100
Seg 3: Base=1327, Limit=580
Seg 4: Base=1952, Limit=96

Logical → Physical:
0,430  → 219+430=649        ✓
1,10   → 2300+10=2310       ✓
2,500  → Limit=100, offset=500 → TRAP!
3,400  → 1327+400=1727      ✓
4,112  → Limit=96, offset=112 → TRAP!
```

---

## 17.3 Segmentation vs Paging

| Metric / Concept | Paging | Segmentation |
|------------------|--------|--------------|
| **Division Unit** | Fixed-size blocks (pages/frames) | Variable-size logical blocks (code, stack, heap) |
| **Programmer View** | Invisible (physical abstraction) | Visible (logical modules) |
| **Internal Fragmentation** | Yes (on last page) | No |
| **External Fragmentation** | No (pages map anywhere) | Yes (variable segments leave holes) |
| **Hardware Table** | Page Table (Page → Frame) | Segment Table (Segment Base + Limit) |

---

## 17.4 Shared Segments
- Two processes can have segments with same base address
- Segments mapped to both → shared memory

---

## 17.5 Linux Angle: Flat Memory Model
- **Legacy x86**: Explicit segmentation registers (CS, DS, SS)
- **Modern Linux (x86-64)**: Flat memory model
  - Kernel sets all segment bases to `0x00000000`
  - Limit = maximum addressable space
  - Effectively neutralizes segmentation

---

## 17.4 Key Takeaways

1. **Segmentation** = variable-size logical units matching programmer view
2. **Logical address** = `<segment#, offset>`
3. **Segment table** = Base + Limit per segment
4. **External fragmentation** = yes (unlike paging)
5. **Segmentation fault** = offset ≥ limit

---

## 17.5 Exam-Relevant MCQ Patterns

- **Q82**: Fundamental difference — paging fixed/transparent, segmentation variable/visible
- **Q83**: Segmentation address translation — offset ≥ limit → trap (segmentation fault)

---

# Topic 18 (Detailed): Paging

**Source**: Lecture 3.4 (Unit 3) + Textbook Ch. 8 (Silberschatz Ch. 8, Stallings Ch. 7)

---

## 18.1 Core Idea

**Key Idea**: Fixed-size frames (physical) + pages (logical) → **No external fragmentation**

---

## 18.2 Paging Basics

### Basic Method
- Divide physical memory into **fixed-size frames**
- Divide logical memory into **same-size pages**
- Page size = frame size (hardware-defined)
- Track all free frames
- Run program of N pages → find N free frames → load
- **Page table** translates logical → physical
- **Internal fragmentation** still exists (last page)

### Page Size
- Hardware-defined: 512 bytes to 1 GB
- Common: 4KB, 8KB
- `getconf PAGESIZE` displays system page size

---

## 18.2 Address Structure

### 32-bit, 4KB Pages
```
Page Number (20 bits) | Page Offset (12 bits)
```

### General Formula
- Page size = 2^d bytes
- Offset bits = d
- Page number bits = address_bits - d

---

## 18.3 Page Table

**Maps page → frame**

### Page Table Entry (PTE)
```
| Frame # | Valid | Prot | Ref | Dirty | ...
```

### PTE Bits
| Bit | Meaning |
|-----|---------|
| **Valid** | Page in memory? (1=yes, 0=on disk/not allocated) |
| **Protection** | Read/Write/Execute permissions |
| **Reference** | Page accessed recently (for LRU/Clock) |
| **Dirty** | Page modified (needs write-back on replacement) |

---

## 18.4 Page Table Size Calculation

### Example: 32-bit, 4KB pages, 4-byte PTE
```
Number of entries = 2^(32-12) = 2^20 = 1,048,576
Size = 2^20 × 4 bytes = 4 MB per process
```

---

## 18.5 Paging Example (Silberschatz)

```
Page size = 2,048 bytes
Process size = 72,766 bytes
Pages = 35 + 1,086 bytes
Internal fragmentation = 2,048 - 1,086 = 962 bytes
Worst case fragmentation = 1 frame - 1 byte
```

---

## 18.6 Free Frames & Frame Table
- OS manages physical memory via **frame table**
- Tracks free/allocated frames
- Page table used by CPU dispatcher for context switch
- Paging increases context-switch time

---

## 18.7 Two-Memory-Access Problem
Without TLB: every access needs 2 memory accesses (page table + data)

---

## 18.8 TLB (Translation Lookaside Buffer)

### Purpose
- Hardware cache for page table entries
- **TLB Hit**: Translation in TLB → fast (bypass page table)
- **TLB Miss**: Walk page table → slow (2+ memory accesses)

### Structure
- Associative hardware cache (parallel lookup)
- Stores recent `<VPN, PPN>` mappings
- Typical size: 64-512 entries
- **ASID** (Address Space ID): Distinguishes processes in TLB

---

## 18.9 Effective Access Time (EAT)

### Formula
```
EAT = α × (t_TLB + t_RAM) + (1-α) × (t_TLB + 2 × t_RAM)
```
Where:
- α = TLB hit ratio
- t_TLB = TLB lookup time
- t_RAM = Main memory access time

### Example
```
α = 80% (0.80), t_TLB = 20 ns, t_RAM = 100 ns
EAT = 0.80 × 120 + 0.20 × 220 = 140 ns
```

### With 2-Level Paging on Miss
```
EAT = α(t_TLB + t_RAM) + (1-α)(t_TLB + 3×t_RAM)
```

---

## 18.9 Multi-Level Page Tables

### 2-Level (32-bit, 4KB pages)
```
p1 (10 bits) | p2 (10 bits) | d (12 bits)
    │            │           │
    ▼            ▼           ▼
Page Dir    Page Table    Frame
```
- Only allocate page tables for used regions
- Reduces memory for sparse address spaces

### 64-bit Systems
- 2-level insufficient → 3, 4, or 5-level paging
- Linux x86-64: 4-level (PML4 → PDPT → PD → PT)

---

## 18.10 Inverted Page Table

- One entry **per physical frame** (not per logical page)
- Used in 64-bit systems (PowerPC, UltraSPARC)
- Lookup via hash table (slower than direct indexing)
- Saves enormous memory for sparse 64-bit address spaces

---

## 18.10 TLB Details

### TLB vs CPU Cache
| Aspect | TLB | CPU Cache |
|--------|-----|-----------|
| Purpose | Speed up address translation | Speed up memory access |
| Timing | At MMU translation | At CPU memory access |

### Memory Protection
- Protection bits per frame (read-only, read-write, execute-only)
- **Valid/Invalid bit**: `valid` = in address space; `invalid` = not in space / on disk
- PTLR (Page Table Length Register) alternative

### Valid/Invalid Bit
- `valid` = page in memory (memory resident)
- `invalid` = page on disk / not in address space
- Demand Paging: mark invalid intentionally to trigger page fault

### Shared Pages
- **Code sharing**: Read-only (reentrant) code shared (text editors, compilers)
- **COW**: fork() shares pages read-only; write triggers copy

---

## 18.11 Effective Access Time (EAT) Problems

### Problem 1
```

```

### Problem 2
```

```

### Problem 3
```
3-level paging, no TLB
Memory accesses for one translation?
```

---

## 18.12 Key Takeaways

1. **Paging** = fixed-size frames + pages → no external fragmentation
2. **Address split** = Page Number | Offset
3. **Page Table** = maps page → frame; PTE has Valid, Prot, Ref, Dirty bits
4. **32-bit, 4KB** → p=20 bits, d=12 bits; page table = 4 MB
5. **Multi-level** = reduce memory for sparse addresses
6. **Inverted** = one entry per frame; scales with physical RAM
7. **TLB** = hardware associative cache for page translations
8. **EAT** = α(t_TLB + t_RAM) + (1-α)(t_TLB + k×t_RAM)

---

# Topic 19 (Detailed): Page Table Structures, TLB & Effective Access Time (EAT)

---

## 19.1 Hardware Support for Page Table

### Page Table in Memory
- **PTBR** (Page Table Base Register): Points to page table
- **PTLR** (Page Table Length Register): Indicates page table size
- Without TLB: every access = 2 memory accesses (page table + data)

### TLB (Translation Lookaside Buffer)
- Special fast-lookup hardware cache (associative memory)
- Solves two-memory-access problem
- Stores recent `<VPN, PPN>` mappings

---

## 19.2 Effective Access Time (EAT)

### Formula
```
EAT = α × (t_TLB + t_RAM) + (1-α) × (t_TLB + 2 × t_RAM)
```
Where:
- α = TLB hit ratio
- t_TLB = TLB lookup time
- t_RAM = Main memory access time

### Example
```
α = 80%, t_TLB = 20 ns, t_RAM = 100 ns
EAT = 0.80 × 120 + 0.20 × 220 = 140 ns
```

### With 2-Level Paging on Miss
```
EAT = α(t_TLB + t_RAM) + (1-α)(t_TLB + 3×t_RAM)
```
(outer page table + inner page table + data frame)

### Practice Problems
1. **TLB hit ratio = 90%, t_TLB=10ns, t_RAM=100ns, 2-level paging → EAT?**
2. **32-bit, 4KB pages, TLB size 64, 1000 accesses, 95% hit → memory accesses saved?**
3. **3-level paging, no TLB → memory accesses for one translation?**

---

## 19.3 TLB (Translation Lookaside Buffer)

### Purpose
- Hardware associative cache for page table entries
- **TLB Hit**: Translation in TLB → fast (bypass page table)
- **TLB Miss**: Walk page table → slow (2+ memory accesses)

### Structure
- Associative hardware cache (parallel lookup)
- Stores recent `<VPN, PPN>` mappings
- Typical size: 64-512 entries
- **ASID** (Address Space ID): Distinguishes processes in TLB

### TLB vs CPU Cache
| Aspect | TLB | CPU Cache |
|--------|-----|-----------|
| Purpose | Speed up address translation | Speed up memory access |
| Timing | At MMU translation | At CPU memory access |

---

## 19.4 Memory Protection

### Protection Bits
- Protection bit per frame: read-only / read-write
- Execute-only bits possible

### Valid/Invalid Bit
- **Valid (1)**: Page in address space, legal
- **Invalid (0)**: Page not in address space / on disk
- Alternative: PTLR (Page Table Length Register)

---

## 19.5 Valid/Invalid Bit & Demand Paging

### Demand Paging
- Mark pages **invalid** intentionally
- Page fault triggers OS to load page
- Pure demand paging: start process with no pages in memory

### Shared Pages
- **Code sharing**: Read-only (reentrant) code shared (text editors, compilers)
- **Reentrant code**: Non-self-modifying, reusable simultaneously
- **Example**: 40 users, 150KB code + 50KB data → 8,000KB without sharing → 2,150KB with sharing

---

## 19.6 Page Table Structures

### Problem: Page Table Size
```
32-bit, 4KB pages:
Entries = 2^20 = 1,048,576
4-byte PTE → 4 MB per process
```

---

## 19.7 Hierarchical (Multi-Level) Page Tables

### 2-Level Paging (32-bit, 4KB)
```
p1 (10 bits) | p2 (10 bits) | d (12 bits)
    │            │           │
    ▼            ▼           ▼
Page Dir    Page Table    Frame
```
- Only allocate page tables for used regions
- Reduces memory for sparse address spaces

### 64-bit Systems
- 2-level insufficient → 3, 4, or 5-level paging
- Linux x86-64: 4-level (PML4 → PDPT → PD → PT)

---

## 19.8 Hashed Page Tables

- Hash function on virtual page number
- Handle collisions via chaining
- Used when address space > physical memory

---

## 19.7 Inverted Page Table

- One entry **per physical frame** (not per logical page)
- Used in 64-bit systems (PowerPC, UltraSPARC)
- Lookup via hash table (slower than direct indexing)
- Saves enormous memory for sparse 64-bit address spaces

### Inverted PTE Structure
```
struct {
    int pid;        // Owning process
    int vpn;        // Virtual page number
    int frame;      // Physical frame
    // ... protection, ref, dirty bits
}
```

### Lookup
```
hash(pid, vpn) → bucket → linear search for (pid, vpn) match
```

### Trade-offs
| Pros | Cons |
|------|------|
| Scales with RAM (not virtual space) | Hash lookup slower than array index |
| One table for all processes | Collisions → chain traversal |
| Saves massive memory for 64-bit | Need separate per-process table for TLB shootdowns |

---

## 19.8 TLB (Translation Lookaside Buffer)

### Purpose
- Hardware cache for page table entries
- **TLB Hit**: Translation in TLB → fast
- **TLB Miss**: Walk page table → slow (2+ memory accesses)

### Structure
- Associative hardware cache (parallel lookup)
- Stores recent `<VPN, PPN>` mappings
- Typical size: 64-512 entries

---

## 19.9 Effective Access Time (EAT)

### Formula
```
EAT = α × (t_TLB + t_RAM) + (1-α) × (t_TLB + 2 × t_RAM)
```
Where:
- α = TLB hit ratio
- t_TLB = TLB lookup time
- t_RAM = Main memory access time

### Example
```
α = 80% (0.80)
t_TLB = 20 ns
t_RAM = 100 ns
EAT = 0.80 × 120 + 0.20 × 220 = 140 ns
```

### With 2-Level Paging on Miss
```
EAT = α(t_TLB + t_RAM) + (1-α)(t_TLB + 3×t_RAM)
```
(outer page table + inner page table + data frame)

### Practice Problems
1. **TLB hit ratio = 90%, t_TLB=10ns, t_RAM=100ns, 2-level paging → EAT?**
2. **32-bit, 4KB pages, TLB size 64, 1000 accesses, 95% hit → memory accesses saved?**
3. **3-level paging, no TLB → memory accesses for one translation?**

---

## 19.9 TLB (Translation Lookaside Buffer)

### Purpose
- Hardware cache for page table entries
- **TLB Hit**: Translation in TLB → fast (bypass page table)
- **TLB Miss**: Walk page table → slow (2+ memory accesses)

### Structure
- Associative hardware cache (parallel lookup)
- Stores recent `<VPN, PPN>` mappings
- Typical size: 64-512 entries

---

## 19.10 Key Takeaways

1. **Multi-level paging** = reduces page table memory; 2-level = 3 memory accesses without TLB
2. **Inverted page table** = one entry per physical frame; scales with RAM not virtual space
3. **TLB** = hardware associative cache for page translations
4. **EAT** = α(t_TLB + t_RAM) + (1-α)(t_TLB + k×t_RAM) where k = page table levels + 1

# Topic 20 (Detailed): Virtual Memory — Demand Paging, Page Faults, Copy-on-Write

**Source**: Lecture 3.6 (Unit 3) + Textbook Ch. 9 (Silberschatz Ch. 9, Stallings Ch. 8)

---

## 20.1 Background: Virtual Memory

### Definition
- **Virtual Memory**: Separation of user logical memory from physical memory
- Allows programs **larger than physical memory**
- Only part of program needs to be in memory
- More programs can run concurrently

### Virtual Address Space
```
Stack: starts at MAX address, grows DOWN
Heap:  starts at low address, grows UP
Hole:  Unused space between stack and heap
```
- No physical memory needed until heap/stack grows to new page
- Enables sparse address spaces with holes for growth
- System libraries shared via mapping into virtual address space
- Shared memory via mapping pages read-write
- Pages shared during `fork()` → speeds process creation

### Shared Library Example
```
40 users × text editor (150KB code + 50KB data)
Without sharing: 40 × 200KB = 8,000 KB
With code sharing: 150KB + 40 × 50KB = 2,150 KB
```

---

## 20.1 Demand Paging

### Core Philosophy
**Pages loaded into physical memory only when referenced** (lazy loading)

- **Valid/Invalid bit** in PTE:
  - **Valid (1)** = page in memory
  - **Invalid (0)** = page on disk or not allocated

---

## 20.2 Page Fault Handling

```
1. Process accesses invalid page → Page Fault Trap
2. OS checks: Valid access? (within VMA, permissions OK?)
3. Find free frame (or victim via replacement)
4. If victim dirty → Write to swap
5. Read requested page from disk into frame
6. Update PTE (frame #, valid=1)
7. Restart faulting instruction
```

---

## 20.3 Minor vs Major Page Fault

| Type | Description | Latency |
|------|-------------|---------|
| **Minor** | Page already in RAM (shared library, free list, COW copy) — **zero disk I/O** | Microseconds |
| **Major** | Page must be read from **disk** | Milliseconds |

---

## 20.4 Copy-on-Write (COW)

### fork() with COW
1. `fork()` shares **all pages read-only** (COW)
2. Parent/child can read freely
3. On **write attempt** → Page Fault (protection violation)
4. OS allocates new frame, copies page, marks read-write
5. Restarts instruction

```c
// COW example
pid = fork();
// Parent and child share ALL pages (read-only)
// Child calls exec() → new program loaded (no COW needed for that)
// Or child modifies variable → COW triggers → private copy made
```

---

## 20.5 Dirty Bit (Modify Bit)

| Value | Meaning |
|-------|---------|
| **0 (Clean)** | Page not modified → overwrite immediately on replacement |
| **1 (Dirty)** | Page modified → **must write back to disk** before replacement (doubles fault time) |

---

## 20.6 Complete Page Fault Flow

```
CPU accesses page
       │
       ▼
MMU checks PTE Valid bit
       │
       ├── Valid=1 → Physical address → Memory access (fast)
       │
       └── Valid=0 → PAGE FAULT TRAP
                        │
                        ▼
              OS Page Fault Handler
                        │
                        ├── Check: Valid access? (VMA, permissions)
                        │
                        ├── Find free frame (or victim via replacement)
                        │
                        ├── If victim dirty → Write to swap
                        │
                        ├── Read page from disk into frame
                        │
                        ├── Update PTE (frame#, valid=1)
                        │
                        └── Restart faulting instruction
```

---

## 20.7 Minor vs Major Page Fault Details

| Aspect | Minor Fault | Major Fault |
|--------|-------------|-------------|
| **Source** | Page in RAM (COW, shared lib, zero-fill) | Page on disk |
| **Disk I/O** | **None** | Required |
| **Latency** | Microseconds | Milliseconds |
| **Example** | COW copy, shared library, zero-fill | First access, swapped out |

---

## 20.8 Copy-on-Write (COW) Details

### Mechanism
```
Hardware Enforcement: OS marks PTEs for BOTH processes as Read-Only
The Trap: If either process writes → MMU triggers protection fault
OS Response: Intercepts trap → allocates new frame → copies data →
             updates PTE to Read/Write → restarts instruction
```

### COW & fork()
```
Parent forks Child
    │
    ├── Both share ALL pages (Read-Only, COW)
    │
    ├── Child calls exec()
    │     └── New address space loaded; COW pages discarded
    │
    └── Child modifies variable
          └── COW triggers → private copy made
```

---

## 20.9 Dirty Bit (Modify Bit)

| Value | Meaning | Replacement Action |
|-------|---------|-------------------|
| **0 (Clean)** | Page not modified | Overwrite immediately (no disk write) |
| **1 (Dirty)** | Page modified | **Must write back to disk** first (doubles fault time) |

---

## 20.10 Page Replacement Need

### When No Free Frame
```
Page fault → No free frame → Page replacement
1. Find victim frame (algorithm)
2. If victim dirty → Write to swap
3. Read requested page into frame
4. Update page/frame tables
5. Restart instruction
```

### Note
- Potentially **2 page transfers** per fault (victim out + new in)
- Increases EAT

---

## 20.11 Linux Implementation: kswapd

### The Problem
- Should OS wait for 0 free frames before replacing?

### Linux Solution: kswapd (Kernel Swap Daemon)
- **Watermarks**: "high" and "low" free memory thresholds
- When free memory < low watermark → kswapd wakes up
- Proactively evicts inactive pages in background
- Builds pool of free frames → programs rarely wait synchronously

---

## 20.12 Mobile/Modern Optimizations

### Compressed Memory (ZRAM)
- Android, macOS/iOS use compressed memory (ZRAM)
- Instead of disk swap: compress inactive page, keep in RAM
- CPU cycles cheaper than disk I/O

---

## 20.13 Key Takeaways

1. **Demand Paging** = load pages on reference (lazy loading)
2. **Page Fault** = trap → check validity → find frame → read from disk → update PTE → restart
3. **Minor Fault** = resolves in RAM (COW, shared lib); **Major Fault** = disk I/O
4. **COW** = fork() shares pages read-only; write triggers private copy
5. **Dirty Bit** = if 0, no write-back needed on replacement

---

## 20.14 Exam-Relevant MCQ Patterns

- **Q84**: Demand paging = load pages on reference (lazy loading)
- **Q85**: Page fault handling — MMU generates trap to OS first
- **Q86**: COW fork — protection violation trap → OS copies page → restarts instruction
- **Q87**: Minor vs Major fault — minor = no disk I/O; major = disk read
- **Q88**: Dirty bit = if 0, no write-back needed on replacement

## 21.7 Clock (Second-Chance) Algorithm

### Algorithm
- Circular list of frames with **reference bit (R)**
- Hand sweeps around:
  - If R=0 → victim (replace)
  - If R=1 → R=0, give second chance, advance hand

### Trace: 3 Frames

```
Initial: all R=0

Ref 1: [1@R=1]           Fault, set R=1
Ref 2: [1@1, 2@1]        Fault, set R=1
Ref 3: [1@1, 2@1, 3@1]   Fault, set R=1
Ref 4: Hand at 1@1→R=1→set 0, advance
       Hand at 2@1→R=1→set 0, advance
       Hand at 3@1→R=1→set 0, advance
       Hand at 1@0→VICTIM! Replace with 4@1
       Frames: [4@1, 2@0, 3@0]
Ref 1: Hand at 2@0→VICTIM! Replace with 1@1
       Frames: [4@1, 1@1, 3@0]
Ref 2: Hand at 3@0→VICTIM! Replace with 2@1
       Frames: [4@1, 1@1, 2@1]
Ref 5: Hand at 4@1→set 0, advance
       Hand at 1@1→set 0, advance
       Hand at 2@1→set 0, advance
       Hand at 4@0→VICTIM! Replace with 5@1
       Frames: [5@1, 1@0, 2@0]
Ref 1: Hit! Set R=1 → [5@1, 1@1, 2@0]
Ref 2: Hit! Set R=1 → [5@1, 1@1, 2@1]
Ref 3: Hand at 5@1→set 0, advance
       Hand at 1@1→set 0, advance
       Hand at 2@1→set 0, advance
       Hand at 5@0→VICTIM! Replace with 3@1
       Frames: [3@1, 1@0, 2@0]
Ref 4: Hand at 1@0→VICTIM! Replace with 4@1
       Frames: [3@1, 4@1, 2@0]
Ref 5: Hand at 2@0→VICTIM! Replace with 5@1
       Frames: [3@1, 4@1, 5@1]
```

**Faults: 9** (same as FIFO here, but no Belady's Anomaly!)

## 21.8 Enhanced Clock (With Dirty Bit)

### 4 Priority Classes (Best → Worst)

| Priority | (Ref, Dirty) | Reason |
|----------|--------------|--------|
| **1 (Best)** | (0, 0) | Not referenced, clean → no write-back |
| **2** | (0, 1) | Not referenced, dirty → needs write-back |
| **3** | (1, 0) | Referenced, clean → recently used |
| **4 (Worst)** | (1, 1) | Referenced and dirty |

### Algorithm
1. Scan for (0,0) — if found, replace
2. If not found, scan for (0,1) — clear ref, advance
3. If not found, scan for (1,0) — clear ref, advance
4. If not found, scan for (1,1) — clear ref, advance
5. Repeat from step 1

**Linux uses variant** of enhanced clock.

---

## 21.9 Frame Allocation

### Strategies

| Strategy | Formula | Example: 62 frames, P1(10 pages), P2(127 pages) |
|----------|---------|--------------------------------------------------|
| **Equal** | `frames / processes` | 31 each |
| **Proportional** | `(size_i / total_size) × total_frames` | P1: (10/137)×62 ≈ **4.5 frames** |
| **Priority** | High-priority gets more | Depends on priority |
| **Working Set** | Pages actively used in recent Δ time | Dynamic |

### Working Set Model
- Based on **Locality of Reference** (spatial + temporal)
- **Working Set Window (Δ)**: Pages referenced in last Δ time units
- Keep working set in memory → prevent thrashing

---

## 21.10 Thrashing

### Definition
High paging activity where CPU spends more time swapping than executing.

### Cause
```
Sum of working-set sizes > Total Physical Memory
Σ WSSᵢ > D
```

### Detection
- CPU utilization drops while disk I/O high
- Page fault rate spikes

### Solutions
1. **Working Set Model** — keep working set in memory
2. **Page Fault Frequency (PFF)** — dynamic frame allocation based on fault rate

### PFF Strategy
- Establish **upper and lower page fault rate bounds**
- If process rate > upper bound → grant more frames
- If process rate < lower bound → revoke frames

---

## 21.11 Global vs Local Replacement

| Policy | Behavior | Risk |
|--------|----------|------|
| **Global** | Victim from any process | One bad process steals frames → system-wide thrashing |
| **Local** | Victim from faulting process only | Isolates thrashing to one process |

---

## 21.12 Key Takeaways

1. **FIFO** = Belady's Anomaly YES; **LRU/OPT** = Belady's Anomaly NO (stack algorithms)
2. **Clock/Second-Chance** = circular queue + reference bit; approximates LRU
3. **Enhanced Clock** = (ref, dirty) priority: (0,0) > (0,1) > (1,0) > (1,1)
4. **Frame Allocation**: Equal, Proportional, Priority, Working Set
5. **Thrashing** = Σ WSSᵢ > D; detected by high paging + low CPU
6. **Working Set** = pages referenced in last Δ time; based on locality
7. **PFF** = upper/lower fault rate bounds → grant/revoke frames
8. **Global replacement** = thrashing contagion risk; **Local** = isolates

---

# Topic 22 (Detailed): NUMA, Memory Locality & Clock Page Replacement

**Source**: Lecture 3.8 (Unit 3) + Textbook Ch. 9 (Silberschatz Ch. 9)

## 22.1 NUMA (Non-Uniform Memory Access)

### Architecture
- Memory access latency varies by CPU-memory distance
- Each CPU has "local" memory (fast) and "remote" memory (slow)
- Multiple nodes: each with CPUs + local RAM, connected via interconnect

### NUMA Components
| Component | Description |
|-----------|-------------|
| **Processors (CPUs)** | Execute processes; access local & remote memory |
| **Local Memory** | Directly connected to CPU; lowest access latency |
| **Remote Memory** | Connected to another CPU; accessed via interconnect |
| **High-Speed Interconnect** | Transfers data between nodes |
| **Memory Controller** | Handles requests, manages data transfer |
| **OS** | Schedules processes, allocates memory for locality |

---

## 22.2 Memory Locality

### Definition
- Tendency of program to access same/nearby memory locations repeatedly
- Basis for efficient memory hierarchy (registers → cache → RAM → virtual memory)

### Benefits
- Reduces memory access time
- Increases CPU cache hit rate
- Decreases cache misses
- Improves virtual memory/paging efficiency

### Types of Locality

| Type | Description | Applications |
|------|-------------|--------------|
| **Temporal** | If location accessed, likely accessed again soon | CPU cache stores recent data; frequent instructions in instruction cache |
| **Spatial** | If location accessed, nearby locations likely next | Cache loads entire cache line; sequential file reading |

---

## 22.3 NUMA Memory Latency

| Access Type | Latency |
|-------------|---------|
| **Local** | ~100ns (direct on CPU's local bus) |
| **Remote** | ~200-400ns (traverse interconnect) |

---

## 22.4 First-Touch Policy
- Page allocated on node where **first touched**
- OS tries to allocate on same node as accessing thread

### Example
```c
// BAD: All memory on master thread's node
double *a = malloc(N * sizeof(double));
#pragma omp parallel for
for (int i = 0; i < N; i++) a[i] = 0.0;

// GOOD: Each thread touches its pages
double *a = malloc(N * sizeof(double));
#pragma omp parallel for
for (int i = 0; i < N; i++) a[i] = 0.0;  // Each thread touches its pages
```

---

## 22.5 NUMA-Aware OS Support

### Linux APIs
```c
#include <numa.h>

// Allocate on specific node
void *ptr = numa_alloc_onnode(size, node);

// Allocate interleaved across nodes
void *ptr = numa_alloc_interleaved(size, nodemask);

// Set preferred node for current thread
numa_set_preferred(node);

// Get current node
int node = numa_node_of_cpu(sched_getcpu());

// Move pages between nodes
move_pages(pid, count, pages, nodes, status, flags);
```

### Scheduler Support
- **Prefers same-node migration**
- **Cross-node** only for severe imbalance
- Tracks NUMA topology

---

## 22.5 NUMA + Page Replacement

### Challenge
- Global replacement may choose remote victim
- Evicting remote page = remote disk I/O (slow)
- Allocating replacement on local node = good

### Solution: NUMA-Aware Replacement
1. Prefer local victims
2. If no local victim, consider remote with penalty
3. Allocate replacement on requesting node

### Linux Implementation
- Per-zone LRU lists (each NUMA node has own LRU)
- `kswapd` runs per node
- Global direct reclaim considers NUMA distance

### Migrate-on-Fault
```
Process on Node 0 accesses page on Node 1:
1. Page fault (page present but remote)
2. Option A: Migrate page to Node 0
   - Allocate local frame
   - Copy content
   - Update PTE
   - Free remote frame
3. Option B: Keep remote, track NUMA hint
   - Increment NUMA fault counter
   - If threshold exceeded → migrate
```

---

## 22.6 Clock Page Replacement (Second-Chance)

### Basic Algorithm
- Circular list of frames with **reference bit (R)**
- Hand sweeps around:
  - If R=0 → victim (replace)
  - If R=1 → R=0, give second chance, advance hand

```
Frame:  [P1,1] [P2,0] [P3,1] [P4,1] [P5,0]
              ↑ hand
```

### Logic
```
while (true):
    if frame[hand].ref == 0:
        victim = hand
        break
    else:
        frame[hand].ref = 0  // second chance
        hand = (hand + 1) % N
```

---

## 22.7 Enhanced Clock (Second-Chance with Dirty Bit)

### 4 Priority Classes (Best → Worst)

| Priority | (Ref, Dirty) | Reason |
|----------|--------------|--------|
| **1 (Best)** | (0, 0) | Not referenced, clean → no write-back |
| **2** | (0, 1) | Not referenced, dirty → needs write-back |
| **3** | (1, 0) | Referenced, clean → recently used |
| **4 (Worst)** | (1, 1) | Referenced and dirty |

### Algorithm
1. Scan for (0,0) — if found, replace
2. If not found, scan for (0,1) — clear ref, advance
3. If not found, scan for (1,0) — clear ref, advance
4. If not found, scan for (1,1) — clear ref, advance
5. Repeat from step 1

**Linux uses variant** of enhanced clock.

---

## 22.6 Clock Algorithm Example (Trace)

**Reference String**: `1, 2, 3, 2, 4, 1`
**Frames**: 3
**Initial**: all R=0

| Step | Ref | Frame States (Page, R) | Action |
|------|-----|------------------------|--------|
| 1 | 1 | [1,0], [-,0], [-,0] | Fault, set R=1 |
| 2 | 2 | [1,1], [2,1], [-,0] | Fault, set R=1 |
| 3 | 3 | [1,1], [2,1], [3,1] | Fault, set R=1 |
| 4 | 2 | [1,1], [2,1], [3,1] | Hit, set R=1 |
| 5 | 4 | Hand: 1@1→0, 2@1→0, 3@1→0, 1@0→VICTIM! → [4,1], [2,0], [3,0] | Fault |
| 6 | 1 | Hand: 2@0 → VICTIM! → [4,1], [1,1], [3,0] | Fault |

---

## 22.7 Enhanced Clock Algorithm Details

### Multi-Pass Algorithm
```
Pass 1: Scan for (0,0) — replace immediately if found
Pass 2: Scan for (0,1) — clear ref, advance; if completes → write dirty, replace
Pass 3: Scan for (1,0) — clear ref, advance
Pass 4: Scan for (1,1) — clear ref, advance
Repeat from Pass 1
```

### Why (0,0) First?
- **No disk write needed** → fastest replacement
- Clean page → can be overwritten immediately
- Unreferenced → unlikely to be needed soon

### Why (1,1) Last?
- **Recently used** → likely to be used again
- **Modified** → requires disk write before replacement
- **Maximum cost to replace**

## 22.8 Complete Exam-Focused Summary

| Concept | Key Points |
|---------|------------|
| **NUMA** | Local memory ~100ns, remote ~200-400ns |
| **First-touch** | Page allocated on node where first written |
| **NUMA scheduler** | Prefers same-node migration; cross-node for severe imbalance |
| **Clock Algorithm** | Circular + R bit; R=1→reset to 0, advance; R=0→replace |
| **Enhanced Clock** | 4 passes by (R,D): (0,0)>(0,1)>(1,0)>(1,1) |
| **Pass 0: (0,0)** | Best - no I/O needed |
| **Pass 3: (1,1)** | Worst - recently used + dirty |
| **Linux** | Uses enhanced clock variant |
