Slide 4, 5 & 6: Concurrency vs. Parallelism in Multicore Systems
--------------------------------------------------------------------------------
• Architecture Shift:
  - Evolution from single-CPU systems to multi-CPU machines, and ultimately to **Multicore Processors** where multiple computing cores reside on a single semiconductor chip.
  - Each core appears as an independent physical CPU to the operating system scheduler.

• Silberschatz Figure 4.3 & 4.4: Concurrency vs. Parallelism:

  CONCURRENT EXECUTION ON A SINGLE-CORE SYSTEM (Time Slicing / Interleaved):
  Core 1: [ T1 ][ T2 ][ T3 ][ T4 ][ T1 ][ T2 ][ T3 ][ T4 ] --------> Time

  PARALLEL EXECUTION ON A MULTICORE SYSTEM (Simultaneous Execution):
  Core 1: [     T1     ][     T3     ][     T1     ][     T3     ] -> Time
  Core 2: [     T2     ][     T4     ][     T2     ][     T4     ] -> Time

• Conceptual Distinction:
  - Concurrency: More than one task is making progress by interleaving execution over time on a single processing core.
  - Parallelism: Multiple tasks are executing simultaneously at the exact same physical instant on separate hardware cores.

Slide 7 & 8: Multicore Programming Challenges & Types of Parallelism
--------------------------------------------------------------------------------
• Five Key Multicore Challenges:
  1. Identifying Tasks: Analyzing applications to locate distinct, independent areas of computation that can run concurrently.
  2. Balance: Ensuring that parallel tasks execute roughly equal amounts of work with equal computational value so cores do not sit idle.
  3. Data Splitting: Partitioning input and output data structures cleanly so separate cores manipulate distinct data chunks.
  4. Data Dependency: Synchronizing tasks when one thread depends on intermediate data generated by another thread to avoid race conditions.
  5. Testing and Debugging: Concurrency introduces non-deterministic execution timing, making concurrency bugs, deadlocks, and race conditions difficult to reproduce.

• Types of Parallelism:
  1. **Data Parallelism**:
     - Distributes subsets of the same data across multiple computing cores.
     - Each core performs the identical operation on its local data slice (e.g. array element-wise addition, matrix multiplication, image filtering).
  2. **Task Parallelism**:
     - Distributes distinct tasks (threads) across multiple computing cores.
     - Each thread executes a unique algorithm or function. Threads may operate on the same data or different data.

Slide 9 to 14: Multithreading Models
--------------------------------------------------------------------------------
• User Threads vs. Kernel Threads:
  - User Threads: Managed entirely in user space by a thread library without kernel system calls. Fast to create and switch, but kernel sees only one process.
  - Kernel Threads: Managed and scheduled directly by the OS kernel. Capable of true multicore parallelism.

• Silberschatz Figures 4.5 - 4.8: The Four Architectural Models:

  1. MANY-TO-ONE MODEL (Silberschatz Figure 4.5):
     User Threads:    (T1)   (T2)   (T3)   (T4)
                       \      |      |      /
                        \     |      |     /
     Kernel Thread:            [ KT1 ]
     - Properties: Many user threads multiplexed to a single kernel thread.
     - Pitfall: If one user thread executes a blocking system call, the entire process blocks.
     - Cannot execute in parallel across multicore CPUs.
     - Examples: Solaris Green Threads, GNU Portable Threads.

  2. ONE-TO-ONE MODEL (Silberschatz Figure 4.6):
     User Threads:    (T1)     (T2)     (T3)     (T4)
                       |        |        |        |
     Kernel Threads: [ KT1 ]  [ KT2 ]  [ KT3 ]  [ KT4 ]
     - Properties: Each user thread has a dedicated kernel thread peer.
     - True multicore parallelism: A blocking call in T1 does not stop T2.
     - Overhead: Creating user threads incurs kernel thread allocation cost.
     - Current Industry Standard: Linux, Windows, modern Solaris.

  3. MANY-TO-MANY MODEL (Silberschatz Figure 4.7):
     User Threads:    (T1)   (T2)   (T3)   (T4)   (T5)   (T6)
                        \     /      |      |      \     /
     Kernel Threads:    [ KT1 ]   [ KT2 ]   [ KT3 ]
     - Properties: Multiplexes many user-level threads to a smaller or equal number of kernel threads.
     - Developers can create arbitrary user threads without overwhelming the kernel.
     - Achieves both responsiveness and multicore parallelism.

  4. TWO-LEVEL MODEL (Silberschatz Figure 4.8):
     User Threads:    (T1)   (T2)   (T3)   (T4)     (T_bound)
                        \     /      |      |           |
     Kernel Threads:    [ KT1 ]   [ KT2 ]            [ KT_bound ]
     - Hybrid: Supports M:M multiplexing, but allows critical user threads (e.g. real-time audio) to be permanently bound to a dedicated kernel thread.
     - Examples: IRIX, HP-UX, Tru64 UNIX, Solaris 8 and earlier.

Slide 15 to 19: POSIX Pthreads Library & APIs
--------------------------------------------------------------------------------
• Standards:
  - POSIX standard (IEEE 1003.1c) specification for thread creation and synchronization.
  - Widely implemented in Linux, macOS, Unix.

• Thread Creation: pthread_create():
  #include <pthread.h>
  int pthread_create(pthread_t *thread, const pthread_attr_t *attr,
                     void *(*start_routine)(void *), void *arg);
  - `thread`: Pointer to pthread_t variable storing the thread handle / ID.
  - `attr`: Pointer to attribute struct (`NULL` for defaults).
  - `start_routine`: Function pointer to the thread runner (`void *func(void *arg)`).
  - `arg`: Pointer to arguments passed to the runner.
  - **Critical Warning (Stack-Escape Bug)**:
    Never pass the address of a local stack variable to `pthread_create()` if the calling function might return before the thread executes! Always allocate argument data on the Heap (`malloc`), use Global memory, or pass from `main()` stack.

• Synchronizing Execution: pthread_join():
  int pthread_join(pthread_t thread, void **retval);
  - Blocks the caller until target `thread` terminates.
  - `retval`: Receives return value / exit code passed from the target thread.
  - **Zombie Prevention**: If a non-detached thread is not joined, its descriptor remains in memory as a Zombie Thread.

• Silberschatz Figure: Fork-Join Parallel Pattern:
  Main Thread --------------+----------------------------+-------------> Aggregates Results
                            | pthread_create()           | pthread_join()
                            v                            ^
                      Worker Thread ---------------------+ pthread_exit()

• Explicit Termination: pthread_exit():
  void pthread_exit(void *retval);
  - Calling `pthread_exit(0)` inside `main()` causes the main thread to terminate while keeping the process and background worker threads running until all workers finish.
  - Conversely, calling `exit(0)` or `return 0` in `main()` immediately kills the entire process and terminates all running threads abruptly.

Slide 20, 21 & 22: Complete Pthreads C Implementation
--------------------------------------------------------------------------------
• Program: Multi-threaded Summation Calculator:
  #include <pthread.h>
  #include <stdio.h>
  #include <stdlib.h>

  int sum; /* Shared global variable across threads */

  void *runner(void *param); /* Thread runner function prototype */

  int main(int argc, char *argv[]) {
      pthread_t tid;       /* Thread identifier */
      pthread_attr_t attr;  /* Set of thread attributes */

      if (argc != 2) {
          fprintf(stderr, "usage: a.out <integer value>\n");
          return -1;
      }
      if (atoi(argv[1]) < 0) {
          fprintf(stderr, "%d must be >= 0\n", atoi(argv[1]));
          return -1;
      }

      /* Initialize default thread attributes */
      pthread_attr_init(&attr);

      /* Create the worker thread */
      pthread_create(&tid, &attr, runner, argv[1]);

      /* Wait for worker thread to complete */
      pthread_join(tid, NULL);

      printf("sum = %d\n", sum);
      return 0;
  }

  /* The thread begins control in this function */
  void *runner(void *param) {
      int i, upper = atoi(param);
      sum = 0;
      for (i = 1; i <= upper; i++) {
          sum += i;
      }
      pthread_exit(0);
  }

• Concurrency Diagnostic Analysis (Slide 22):
  - Thread Execution Order: Non-deterministic; depends on OS CPU scheduling.
  - Thread Join Order: If main loops through thread IDs sequentially, joins occur in that order, but threads may exit in arbitrary order.
  - Safety Warning: If multiple threads update a shared variable (like `sum`) without mutex synchronization, a **Race Condition** occurs producing corrupted outputs.

Slide 25 to 28: Thread Scheduling Scopes (PCS vs. SCS)
--------------------------------------------------------------------------------
• Two Contention Scopes:
  1. **Process-Contention Scope (PCS)**:
     - In Many-to-One and Many-to-Many architectures.
     - User-level thread library schedules user threads onto available kernel LWPs.
     - Competition for CPU execution is confined strictly among threads of the **same process**.
  2. **System-Contention Scope (SCS)**:
     - The operating system kernel scheduler directly assigns kernel threads onto physical CPU cores.
     - Competition for CPU execution occurs among **all threads across the entire system**.
     - Used in One-to-One models (Linux, macOS, Windows).

• POSIX Pthread Scope API:
  #include <pthread.h>
  #include <stdio.h>

  pthread_attr_t attr;
  pthread_attr_init(&attr);

  // Set scheduling scope to System-Contention Scope:
  pthread_attr_setscope(&attr, PTHREAD_SCOPE_SYSTEM);

  // Set scheduling scope to Process-Contention Scope:
  // pthread_attr_setscope(&attr, PTHREAD_SCOPE_PROCESS);

Slide 29: Advanced Thread Management (Thread Pools & Cancellation)
--------------------------------------------------------------------------------
• Thread Pools:
  - Repeated thread creation and destruction introduces overhead and can lead to resource exhaustion if hundreds of concurrent requests arrive.
  - Architecture: Creates a pool of worker threads at startup that sleep waiting for tasks submitted to a work queue.
  - Once a thread completes its task, it returns to the pool to await new work rather than terminating.
• Thread Cancellation:
  - Terminating a thread before its execution completes (e.g. canceling an image download).
  - Modes:
    1. **Asynchronous Cancellation**: One thread terminates the target thread immediately. Dangerous because target may hold mutexes or allocated resources leading to leaks and deadlocks.
    2. **Deferred Cancellation**: The target thread periodically checks cancellation points (`pthread_testcancel()`) to safely terminate when it is in a consistent state.
